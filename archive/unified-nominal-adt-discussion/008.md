## Decision 8: Reflection

My recommendation is:

> `Mirror` remains a sealed, capability-bearing view of a value’s callable surface. It may describe a family’s public schema, but it does not open an instance’s representation or become a second case-analysis mechanism.

This preserves everything Gel needs while keeping exhaustive elimination authoritative.

### 1. Preserve the existing reflection architecture

The current division remains sound:

- `(Mirror of value)` creates an explicit reflective boundary.
- `(mirror messages)` returns unique callable selectors.
- `(mirror signatures)` returns one opaque `Signature` for each overload row.
- `(mirror invoke signature ...)` invokes that exact row.
- `(signature accepts? candidate)` checks argument compatibility without invoking.
- `(mirror subject)` returns the original value under an expected runtime-checked type.
- `(mirror raw)` returns structural diagnostic text.

Reflection messages remain on `Mirror`, not on every Aloe value.

There is still:

- no `perform`;
- no dynamic send from a `Symbol`;
- no user construction of `Signature` values;
- no second overload search during reflective invocation.

A selector symbol describes a row but grants no authority to invoke it. The opaque `Signature` is the authority.

### 2. Reflection follows the dynamic nominal receiver

When a value enters `Mirror`, its original static view is not retained.

If a family value was statically known only as a protocol, its mirror still describes the actual runtime family’s public reflective surface. This is the explicit dynamic hatch that makes tools such as Gel useful.

However, the mirror does not retain or manufacture constructor-set refinement. It describes the runtime receiver according to the safe surface rules below.

Protocol conversion therefore does not create a protocol wrapper, and mirroring does not reveal a hidden wrapper.

### 3. Callable surfaces by receiver kind

The reflected rows should be:

| Mirrored subject | Reflected callable rows |
| --- | --- |
| Multi-constructor family instance | Whole-family messages only |
| One-constructor family instance | Whole-family messages plus the sole constructor’s local messages and payload accessors |
| Family type object | Representation constructors and factories |
| Primitive value or type object | Its existing public primitive rows |
| Host capability | Rows declared by its exact host interface |
| A `Mirror` itself | The reflection API of `Mirror` |

The last row preserves the existing distinction: asking an existing mirror for its signatures describes its stored subject. Explicitly constructing `Mirror of mirror` reflects the `Mirror` value itself.

#### Why multi-constructor local messages are excluded

Exposing the actual constructor’s local rows from an unrefined `Mirror` would make method presence an implicit case predicate. Reflective invocation could then call case-local operations without passing through exhaustive elimination.

Therefore, for a multi-constructor family:

- actual-constructor local messages do not appear in `messages`;
- their rows do not appear in `signatures`;
- payload accessors do not appear;
- creating a mirror inside a singleton-refined branch does not capture an escaping refinement certificate.

A one-constructor family is different because every value necessarily has its sole constructor. Exposing its local surface cannot discriminate among cases and preserves current `Point`-style reflection.

### 4. Family schema is reflected through its type object

A family’s type object exposes its public construction surface:

- every representation constructor appears as an exact signature row;
- every factory appears as an exact signature row;
- constructor rows occur in constructor declaration order;
- overloaded factories retain one row per overload.

This lets tooling discover the complete public constructor inventory without asking which constructor an arbitrary instance currently contains.

Constructor signatures reveal:

- the constructor selector;
- ordered payload types through the existing parameter description;
- the family result type;
- declared generic parameters;
- that the row is a representation constructor rather than a factory.

Payload position names need not become reflective data initially. Decision 4 made payload order and arity semantic; source parameter names are not required to invoke or exhaustively bind a constructor.

There is no separate first-class `Constructor` token in Aloe source. The opaque signature row is sufficient for checked reflective construction, while its selector and type data provide presentation metadata.

### 5. Signature role and generic metadata

`Signature` needs enough additional descriptive metadata to distinguish the semantic kinds established by earlier decisions.

Each signature should report a role from a small kernel-defined vocabulary:

- `constructor`
- `factory`
- `family`
- `local`
- `operation`

Here, `operation` covers callable rows belonging to primitives, `Mirror`, and host capabilities that are not algebraic family or type-object rows.

A per-constructor implementation of a whole-family message still appears as one `family` signature. Reflection describes the public operation, not the hidden collection of constructor-indexed bodies.

A signature should also report its declared row-level generic parameters as presentation symbols. Its parameter and return descriptions continue to use the existing reified type grammar of `Symbol` and `List` values.

The precise selector spellings for these new queries can wait for Decision 9. Semantically, tooling must be able to obtain:

```text
selector
role
generic parameters
parameter types
return type
```

Family type arguments already fixed by an instance are substituted into its reflected method types. Fresh row-level generic parameters remain visible as variables.

### 6. Reified type data is descriptive, not authoritative

The existing `Symbol` and `List` representation of types remains presentation data.

For example, a signature may describe a type using data resembling:

```text
Option
(Option Int)
(Result T Error)
```

This data is useful for menus, documentation, diagnostics, and display, but it is not:

- a first-class type object;
- an opaque nominal identity;
- a cast token;
- acceptable as a source type annotation at runtime;
- sufficient to establish that same-spelled nominal families are identical.

Same-named declarations may produce the same descriptive spelling. Exact runtime checks continue to use hidden nominal identities held by mirrors and signatures.

The initial design does not add a general first-class `Type` descriptor or a direct operation for comparing arbitrary runtime types. Gel’s actual requirement is already served more safely by `Signature.accepts?`.

### 7. What instance reflection does not expose

A mirror of a multi-constructor family instance does not programmatically expose:

- the current constructor identity;
- the current constructor name as an authoritative tag;
- a `constructor?` predicate;
- the payload values;
- indexed payload access;
- constructor-local signatures;
- the checker’s constructor-set refinement;
- an opaque family or constructor identity token;
- the family’s conformance list;
- method bodies, dispatch tables, source locations, or closure representation.

Most importantly, there is no operation equivalent to:

```text
(mirror constructor)
(mirror payload)
(mirror is-constructor? Some)
```

Those would reproduce partial pattern matching through reflection and evade missing-case diagnostics.

To consume an instance’s representation, code must:

- use the exhaustive case form;
- call an appropriate whole-family operation;
- or use an explicitly declared protocol implemented exhaustively by the family.

A generic inspector that genuinely needs semantic decomposition can request an `inspect`, `fold`, serialization, or visitor-like protocol. The family then implements that operation with explicit exhaustive knowledge.

### 8. Static refinements are not runtime metadata

Constructor-set refinements are checker facts about an occurrence, not fields stored in a value.

Consequently:

- `Mirror of` does not preserve the expression’s refinement;
- a mirror created from direct `Some` construction is observationally the same kind of mirror as one created from an unrefined `Option`;
- `(mirror subject)` returns the original value, but its usable static type comes from the expected context;
- unwrapping does not recover an earlier branch refinement.

If the expected type of `subject` is a concrete family, the returned value may then be handled with the ordinary exhaustive case form. That is a normal checked elimination, not reflective discrimination.

### 9. Signature identity and ownership

A `Signature` remains an unforgeable capability identifying one exact dispatch row.

Its hidden ownership includes enough information to validate:

- the exact family instantiation for instance rows;
- the exact family type object for constructor and factory rows;
- the appropriate constructor identity for reflectable local rows;
- the exact primitive or host-interface identity;
- the exact overload row.

Therefore:

- a signature from `Option Int` cannot be applied to `Option String`;
- a same-spelled row from an unrelated family is not interchangeable;
- a host row cannot be transferred to a same-named but distinct host interface;
- a family-message row works for every constructor of its owning family;
- a constructor signature works only with the owning family’s type-object mirror.

Ownership is checked by opaque identity, never by the exposed selector or type-description data.

Signature values may be stored and copied. Aloe does not promise meaningful user-visible equality, ordering, hashing, or stable serialization for them. Repeated reflection may produce functionally equivalent capabilities without exposing whether they are the same allocated object.

### 10. Reflective invocation

`Mirror.invoke` continues to invoke the selected row directly. It does not turn the signature’s selector back into a dynamic send and does not rerun overload resolution.

Invocation checks:

1. signature ownership against the target mirror;
2. argument count;
3. each argument against the exact instantiated parameter type;
4. complete resolution of generic arguments;
5. the result against the instantiated return type.

For an instance method, the receiver family’s generic arguments are already fixed.

For a generic constructor or factory on a family type object, row variables are instantiated freshly for each invocation, using the same sources of constraints as an ordinary send:

- explicit static information;
- expected result type;
- argument types;
- enclosing-expression constraints.

Reflection does not make an otherwise ambiguous parameterless `None` constructible. Unresolved generic arguments still cannot escape the checking unit.

The checker may continue to use an expected result type for invocation through a signature variable, because the row itself is not statically known. The runtime validates the actual result against the opaque selected row.

### 11. `Signature.accepts?`

The existing deliberately narrow operation remains:

- it applies to one-parameter rows;
- it checks the candidate mirror’s subject using the same runtime type relation as invocation;
- it does not invoke anything;
- it does not select among overloads;
- it returns `#f` for other arities.

For a generic one-parameter row, its input variables may be solved freshly from the candidate. A `#t` answer means that the candidate can satisfy that parameter position. It does not promise that unrelated result-only type variables are fully determined or that an invocation would type-check without additional context.

There is no need yet for arbitrary-arity argument-list reflection.

### 12. Ordering and overload visibility

Reflection is operationally useful to Gel only if its order is deterministic.

Within one finalized program image:

- constructor rows follow constructor declaration order;
- declaration-owned method and factory rows follow textual declaration order;
- additive extension rows follow their finalized program-definition order;
- overloads remain separate signature rows;
- `messages` removes duplicate selectors while preserving the first signature occurrence.

A whole-family method implemented with constructor-specific bodies contributes one overload row, not one row per body.

Adding a constructor, factory, method, or overload may intentionally change later menu positions. A future module system may need a stronger ordering rule, but that does not need to be invented now.

### 13. Raw output is observable but not a discriminator contract

Decision 7 established that raw output identifies the constructor of a multi-constructor value for human diagnostics. A program can compare any `String`, so reflection cannot make textual branching physically impossible.

The semantic boundary is instead:

- raw text provides no constructor identity;
- it supplies no payload values;
- it grants no signature authority;
- it produces no static refinement;
- it is not an exhaustive or parseable representation contract.

Code that parses `raw` or branches on `show` output is merely branching on presentation text. Aloe does not treat that as correct case analysis and cannot provide missing-case diagnostics for it.

The supported semantic operation for constructor discrimination remains the exhaustive case form.

### 14. Consequences for existing applications

Gel retains everything it needs:

- heterogeneous stack slots remain `Mirror` values;
- menus still enumerate exact overload rows;
- `Signature.accepts?` still filters one-argument rows;
- `Mirror.invoke` still invokes the selected row;
- `subject` and `raw` retain their present roles.

A mirrored `Point` continues to expose `x` and `y` because `Point` has one constructor.

A mirrored `Option Int` instance exposes its whole-family operations but not `Some` payload access or a `None`/`Some` tag. Mirroring the `Option` type object exposes the public `None` and `Some` constructor signatures and identifies them as constructors.

MPL continues to benefit from dynamic concrete reflection: a protocol-typed `Math` value can reveal its concrete family’s whole-family overloads. Constructor-local implementation details remain hidden.

Host capability reflection remains derived from its exact host-interface declaration. The new family model does not weaken that ownership boundary.

The receiver-shaped case form is syntax, not a message, so it never appears in `messages` or `signatures`.

### 15. Alternatives I would reject

I would reject:

- **Reflection messages on every value:** pollutes every protocol and base surface.
- **Dynamic `perform` from a selector symbol:** discards exact-row ownership and duplicates send.
- **Exposing the current constructor token:** creates an unchecked typecase facility.
- **Exposing arbitrary payload values:** bypasses exhaustive elimination and local access rules.
- **Reflecting multi-constructor local rows:** permits case discovery and invocation through method presence.
- **Capturing branch refinement inside an escaping mirror:** turns `Mirror` into a hidden proof object.
- **User-created signatures:** makes selectors and handwritten type descriptions forgeable authority.
- **Ownership checks by name:** breaks nominal isolation.
- **Reflecting each constructor-specific family body separately:** exposes implementation layout instead of the public method row.
- **A general first-class `Type` universe now:** substantially enlarges Aloe without application pressure.
- **Hiding constructor/factory distinction:** prevents tooling from understanding the construction model approved in Decision 2.

### Semantic nucleus

The compact rule is:

> A `Mirror` may tell a program what public operation it holds authority to invoke. It may describe a family’s public constructors through the family type object. It may not tell a program which constructor an arbitrary multi-constructor instance currently contains or extract that instance’s representation.

That preserves reflection as a useful, explicit dynamic tool while keeping nominal identity opaque, constructor refinement static, and exhaustive case analysis authoritative.

I recommend adopting this as Decision 8. I’ll stop here for review before recording it or moving to Decision 9.
