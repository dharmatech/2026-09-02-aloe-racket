# Decision 2: What happens when Aloe sends a construction message to a type object?

The recommended rule is:

> A type object is one ordinary, exactly typed receiver whose message table contains distinguished representation-constructor rows and ordinary type-object method rows. Every send uses Aloe’s existing receiver-first lookup; the selected row determines whether the send directly constructs a case or executes a factory body.

This preserves one send universe while giving constructors enough semantic identity for exhaustiveness and refinement.

## 1. One type object per declaration

A nominal declaration creates one value-level type object, regardless of how many generic instantiations its family may have.

Conceptually:

| Expression receiver | Static identity |
|---|---|
| `Point` | type object for the `Point` declaration |
| `Option` | type object for the `Option` declaration |
| `EntryKind` | type object for the `EntryKind` declaration |

There are not separate runtime objects for `Option Int`, `Option String`, and so forth. Generic arguments instantiate individual constructor or factory sends, not the type object itself.

This matters for Aloe’s character:

- The type name remains the obvious receiver.
- Gel can put that receiver on its stack and enumerate its construction API.
- The editor knows the exact declaration from the receiver’s static type.
- Type-object identity does not multiply through generic instantiations.
- Type expressions do not acquire an expression-position meaning.

The type object is not an instance of the family. `Option` and an `Option Int` value therefore have different message surfaces.

## 2. The type-object message table

A type object owns two semantic kinds of row:

1. Representation-constructor rows.
2. Ordinary type-object method rows.

“Factory” is a useful role for an ordinary type-object method returning a family value; it is not a third runtime entity.

A representation constructor has:

- A unique selector within its family.
- One constructor identity.
- An ordered, typed payload.
- The family’s type parameters.
- A result consisting of the family type refined to that constructor.
- No arbitrary user body.

An ordinary type-object method has:

- A selector and parameters.
- A declared result type.
- An ordinary Aloe body.
- Optional method-local type parameters.
- No constructor identity and no exhaustiveness significance.

A constructor selector should be reserved within its type object: another constructor or factory may not overload it. Factories may overload one another using Aloe’s normal overload rules.

This restriction keeps a constructor selector in one-to-one correspondence with a case identity. Seeing `some`, `none`, or `directory` on a type object therefore has an unambiguous representational meaning. Multiple convenience APIs remain available under descriptive factory selectors such as `at`, `random`, or `from-list`.

## 3. Constructor lookup

Using the provisional send spellings from the handoff, not committing declaration syntax:

```alo
(Point new 1 2)
(Option some 3)
(Option none)
```

Lookup proceeds as an ordinary send:

1. Evaluate the receiver, obtaining an exact type object.
2. Evaluate arguments from left to right.
3. Look up the literal selector on that type object.
4. Check arity and argument types.
5. Execute the selected row.

If it is a representation-constructor row, execution directly creates the declared case with its immutable payload. If it is an ordinary row, its Aloe body executes normally.

There is no separate constructor-call expression, generic-function call, or namespace lookup rule.

The errors remain familiar:

- Unknown selector: unknown message.
- Wrong constructor arity: constructor-specific arity error.
- Payload mismatch: identify the constructor and payload position.
- Conflicting generic evidence: identify the family parameter and constraints.
- Ambiguous factory overload: ordinary ambiguity error.
- Duplicate or reserved constructor selector: declaration error.

## 4. Constructor types

For a family `F` with parameters `A…` and constructor `C` with payload types `P…`, the constructor row behaves as a freshly instantiated polymorphic message on every send:

```text
C : P… → F A… refined-to C
```

This is metalanguage, not proposed Aloe syntax.

For example:

```text
Some : T → Option T refined-to Some
None :     Option T refined-to None

Leaf   : T → Tree T refined-to Leaf
Branch : Tree T, Tree T → Tree T refined-to Branch
```

The refined result remains the ordinary family type. It merely carries the checker’s knowledge that the possible constructor set is a singleton.

Therefore a direct constructor result may immediately use its case-specific surface. Passing it into a context expecting the whole family forgets that refinement.

A factory result receives only its declared result type. A factory that happens always to return `Some` does not expose a `Some` refinement through body inspection. That would make public typing depend on implementation details. In a one-constructor family such as `Point`, this distinction is invisible because the family already has only one possible constructor.

## 5. Bidirectional generic inference

Constructor checking combines three possible sources of type information:

1. An explicit static family instantiation, if supplied.
2. The expected result type.
3. Constructor payload arguments.

The checker creates fresh variables for the family parameters, applies every available constraint, and requires them to agree.

Payload arguments are checked against their substituted payload types rather than merely inferred in isolation. This preserves bidirectional typing for payloads such as function values.

### Representative results

| Construction | Context | Result |
|---|---|---|
| `Point new 1 2` | none | `Point Int`, refined to its sole constructor |
| `Option some 3` | none | `Option Int`, refined to `Some` |
| `Option some 3` | expected `Option Int` | same result |
| `Option some 3` | expected `Option String` | type error |
| `Option none` | expected `Option Int` | `Option Int`, refined to `None` |
| `Option none` | no contextual or explicit type | unresolved `T` error |
| `Result ok 3` | expected `Result Int String` | valid `Ok` result |
| `Result ok 3` | no other information | unresolved error parameter |
| `Tree branch (Tree leaf 1) (Tree leaf 2)` | none | `Tree Int`, refined to `Branch` |

An expected protocol type cannot determine family arguments. If a constructor produces a family conforming to `Math`, an expected `Math` can accept the result, but it cannot reveal whether an otherwise undetermined family parameter should be `Int`, `String`, or something else.

## 6. Unresolved parameters may survive locally—but not escape

A constructor should not fail immediately merely because one parameter is temporarily unknown. Enclosing bidirectional checking may still determine it.

For example, a payload-free `None` branch may be checked before a sibling `Some 3` branch. Both constrain the enclosing branch result, ultimately yielding `Option Int`.

The rule should be:

> Constructor type variables may remain unsolved while checking an enclosing expression, but every family argument must be resolved before the expression’s type escapes its checking unit.

A checking unit includes a top-level definition, standalone evaluated expression, or checked method body.

Consequently, an unannotated top-level value such as a context-free `None` does not silently become polymorphic. Aloe currently has no general let-polymorphism, and constructors should not introduce a constructor-only exception.

The diagnostic should explain the remedy:

```text
cannot infer T for constructor Option.none;
provide an expected Option T or an explicit Option instantiation
```

The eventual surface spelling for explicit instantiation or type ascription belongs to Decision 9. Semantically, it constrains the send; it does not create an instantiated type-object value.

## 7. Runtime generic identity comes from checked construction

The runtime must not attempt to reconstruct every generic argument solely from payloads. That cannot work for `None`, phantom parameters, or the unused error parameter of `Ok`.

A successfully checked constructor send supplies its resolved family instantiation to the resulting value. Thus a value contains, conceptually:

```text
family identity
resolved type arguments
constructor identity
immutable payload
```

This supports exact runtime checks and future reflection without treating `None` as an untyped wildcard.

Unchecked or reflectively assembled constructor invocation will eventually need an equally precise source of type arguments. That belongs to the reflection decision; it should not weaken ordinary checked construction.

## 8. Factories

A factory is an ordinary method on the type object.

For example, a one-constructor `Boid T` family might have:

```alo
(Boid new position velocity)  ; representation constructor
(Boid at position)            ; factory
(Boid random bounds)          ; factory
```

The distinction is semantic:

| Constructor | Factory |
|---|---|
| Directly creates one declared case | Executes an Aloe body |
| Has constructor identity | Has ordinary method-row identity |
| Changes exhaustiveness when added | Does not affect exhaustiveness |
| Result carries case refinement | Result has its declared return type |
| Payload is the stored representation | Arguments need not resemble representation |
| Cannot return another case | May choose among cases or reuse a value |

A factory may be generic per send. Because the type object itself is not instantiated, its generic parameters are fresh method parameters or parameters inferred through its declared family result.

Inside a factory, `self` is the type object, so the body can send a constructor message back to `self`. No special privileged construction operation is necessary.

All representation constructors are initially public. Private constructors and abstract construction rights would introduce access-control and abstraction questions unsupported by current application pressure.

## 9. Constructors are not first-class values

The initial model should expose constructors exclusively as type-object messages.

If a program needs to pass construction behavior, it can wrap the send in an ordinary function object:

```alo
(fn (value) (Option some value))
```

That function still executes through `call`.

Making constructors independently first-class would require answers about:

- How a constructor is extracted from an overloaded type-object surface.
- Whether its generic type is generalized.
- Whether it can be partially applied.
- What receiver owns its reflected signature.
- Whether invoking it still counts as a message to the type object.

None of the current applications requires that additional entity. `Signature` already provides a controlled exact-row handle for reflection, but it should not become ordinary constructor syntax.

## 10. Discovery and tooling

Because a type object has an exact nominal static identity, tooling can enumerate its complete message table without evaluating the program.

For each row, static tooling knows:

- Selector.
- Whether it is a representation constructor or an ordinary method.
- Parameters and result.
- Type parameters.
- Constructor identity, when applicable.
- Whether contextual inference is required.

An editor could present:

```text
Option
  constructors
    none       → Option T
    some T     → Option T

  type messages
    from-list (List T) → Option T
```

This grouping is tooling, not language syntax.

`Mirror` should continue to report type-object selectors and individual signature rows. Whether `Signature` gains observational constructor metadata is Decision 8. Ordinary editor discovery does not need to wait for or depend upon runtime reflection.

## Alternatives considered

### Instantiated type objects

Aloe could make `Option Int` a value-level type object and send `none` to that object. This makes payload-free construction explicit, but it creates runtime type application, additional object identities, caching/equality questions, and a second expression meaning for type notation.

Recommendation: retain one declaration-level type object and make explicit instantiation a static constraint on a send.

### Polymorphically generalized constructor results

A context-free `None` could receive the scheme `∀T. Option T`, allowing a bound `none` value to be reused at several instantiations. This is sound in a language with systematic let-polymorphism, but Aloe currently treats top-level function values as monomorphic. A constructor-only generalization rule would add a surprising exception and complicate runtime type reflection.

Recommendation: require context or explicit instantiation.

### Constructors as ordinary factories

The checker could infer constructor cases from methods that return the family. That cannot reliably distinguish direct representation from computation and gives exhaustiveness no stable declared universe.

Recommendation: constructors are distinguished declaration rows; factories remain ordinary methods.

### Constructor/factory overload sharing

A constructor and factory could share a selector and be distinguished by parameter types. Existing overload machinery could implement this, but selector names would cease to identify cases cleanly in source, diagnostics, reflection, and eventual elimination.

Recommendation: reserve constructor selectors and use descriptive factory selectors.

## Decision 2 recommendation

Approve the following construction model:

- One type object per nominal declaration.
- Constructors and factories are messages on that receiver.
- Representation constructors are distinguished, bodyless rows with stable case identities.
- Constructor selectors are unique and reserved.
- Factories are ordinary, overloadable type-object methods.
- Constructor sends combine explicit, expected, and payload-derived constraints.
- Unresolved parameters may be solved by the enclosing expression but may not escape a checking unit.
- Checked construction records resolved generic arguments in the runtime value.
- Direct constructors yield singleton case refinements; factories expose only declared results.
- Constructors are not independently first-class.
- Static tooling can distinguish constructors from ordinary type-object messages.
