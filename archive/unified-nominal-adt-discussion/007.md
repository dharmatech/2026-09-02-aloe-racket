## Decision 7: Runtime behavior

My recommendation is that nominal algebraic family instances behave as immutable structural values whose nominal identity is carried by opaque runtime identities—not by names.

Conceptually, every family value is:

```text
⟨family-id, resolved-type-arguments, constructor-id, payload-values⟩
```

This is the semantic model, not a required physical representation.

### 1. Family and constructor identity

Each family declaration creates one opaque family identity. Each representation constructor creates one opaque constructor identity owned by that family.

Names do not participate in identity:

- Two families named `Result` are distinct if they come from distinct declarations.
- Constructors named `Some` in two different families are distinct.
- A constructor name cannot be forged by producing the corresponding `Symbol` or `String`.
- Comparing printed names is never a valid runtime type test.
- A constructor identity uniquely determines its owning family.

Names remain important for source lookup, diagnostics, printing, and reflection, but runtime checks use the resolved identities.

Identity is guaranteed within one linked Aloe program image. We should not yet promise that these opaque identities remain stable across separate executions, recompilations, serialization, or a future module-reloading system.

### 2. Instantiated family identity

The runtime type of a generic family value includes its resolved type arguments:

```text
Option Int
Option String
```

are different runtime instantiations of the same nominal family.

Consequently, parameterless constructors still retain their checked instantiation:

```text
Option Int / None
Option String / None
```

These values have the same family declaration and constructor, but different runtime types. This is why constructor inference must be completed by the checker rather than reconstructed from payloads.

Generic arguments remain invariant at runtime, matching Decision 5.

### 3. Values contain data, not behavior

A family value stores its constructor and payload, but does not carry a per-instance method dictionary or closures for its methods.

Behavior belongs to declaration-level metadata:

```text
family identity
    ├── constructor descriptions
    ├── whole-family method rows
    ├── constructor-local method rows
    └── explicit protocol conformances
```

A send uses the value’s family identity, constructor identity when relevant, and the overload rules already established.

This has several consequences:

- Converting a family value to a protocol does not wrap or copy it.
- Widening a constructor refinement does not alter the runtime value.
- Factories leave no provenance in the result. A value remembers which representation constructor produced it, not which factory path led there.
- Adding protocol conformance does not change the representation of existing family values.
- A one-constructor `Point` and a multi-constructor `Option` use the same runtime model.

The implementation may optimize this representation freely as long as none of those choices become observable.

### 4. Immutability and identity observability

A family value’s constructor, type arguments, and payload positions are fixed when the value is created. There are no setters, constructor changes, or payload replacement.

This is shallow semantic immutability:

- A family payload cannot be reassigned.
- A payload may contain an identity-bearing host capability whose external state changes.
- A payload may contain a function or another opaque runtime value.
- The family shell does not make those referenced values deeply immutable.

Ordinary family instances should not expose allocation identity. Two separately allocated values with the same nominal structure are observationally the same data value. The runtime may share, copy, intern, or allocate them independently.

This preserves stable constructor refinement: once a value is known to be `Some`, it cannot later become `None`.

It also ensures ordinarily constructed recursive data is finite and acyclic. Recursive family declarations are allowed, but constructing an immutable node requires its payload values to exist already. Opaque host values and function closures remain leaves from the algebraic value model’s perspective.

### 5. Kernel structural equality

Aloe should retain a small, non-overridable kernel equality used by `check` and other runtime machinery.

Two family values are structurally equal exactly when:

1. they have the same opaque family identity;
2. they have the same resolved runtime type arguments;
3. they have the same opaque constructor identity;
4. corresponding payloads are recursively kernel-equal.

Therefore:

```text
Point(1, 2) == Point(1, 2)       true
Some(1)    == Some(1)            true
Some(1)    == None               false
```

Two structurally identical values from different nominal family declarations are unequal. `None` at `Option Int` and `None` at `Option String` are also unequal at the kernel level.

For payload leaves:

- ordinary scalar and algebraic values use their existing value equality;
- functions, type objects, host capabilities, and other explicitly identity-bearing opaque values compare by their own opaque identity unless that built-in kind already has defined value semantics.

This gives equality a total runtime answer without requiring an `Eq` constraint system before generic families can work.

#### Kernel equality is not an injected `=` method

Defining a family must not silently add a user-visible `=` selector.

If a family or protocol declares `=`, that is an ordinary message and may express domain-specific equality. It does not redefine the kernel relation used by `check`.

This separation matters because user methods may:

- accept a broader protocol argument;
- normalize values before comparison;
- deliberately ignore representation details;
- perform computation or even invoke host capabilities.

None of that should alter the trusted structural comparison used by the language’s testing machinery.

A future explicit equality protocol is possible, but it is not required by this family design.

### 6. Raw printing and user display

Aloe should retain two distinct printing layers.

#### Raw structural rendering

The raw renderer:

- never invokes Aloe methods;
- identifies the nominal family;
- identifies the actual constructor;
- renders payloads in declaration order;
- uses constructor and family names only as labels;
- does not claim to be parseable source or a serialization format.

For example, its information content would resemble:

```text
#<Point 1 2>
#<Option.Some 1>
#<Option.None>
```

The exact punctuation belongs to Decision 9.

For a one-constructor family, the renderer may omit the redundant constructor label, preserving the familiar product-like appearance of `Point`. For a multi-constructor family, it must show the constructor because that distinction is meaningful.

For generic constructors whose payload does not reveal their instantiation, the raw representation should be able to include the resolved type arguments when diagnostic clarity requires it. We can settle whether they are always shown or only shown in detailed output alongside the concrete printing syntax.

Raw output is diagnostic presentation. It is never used to establish nominal identity, equality, or type compatibility.

#### User-facing display

As Aloe does now, normal interactive display may use a whole-family zero-argument `show` message returning `String`.

A multi-constructor family can implement `show` with exhaustive per-constructor bodies. If no suitable `show` operation exists, display falls back to the structural renderer.

The raw path must remain available and must never invoke `show`. That gives debugging and reflection a trustworthy representation even when user display code fails, recurses, or intentionally hides structure.

An implementation may impose clearly marked depth or collection limits for interactive printing. Such truncation affects only presentation, never equality or program semantics.

### 7. Runtime type checks

All runtime boundaries should use one consistent nominal relation.

For an expected concrete family type `F A...`, a value passes when:

- its family identity is exactly `F`;
- its resolved type arguments exactly match `A...` invariantly.

When an internal refined type is relevant, its constructor must additionally belong to the permitted constructor set.

For an expected protocol `P`, a family value passes when its exact family declaration explicitly conforms to the opaque identity of `P`. The value’s constructor is irrelevant because conformance belongs to the family.

No runtime check succeeds because:

- family names match;
- constructor names match;
- payload layouts happen to match;
- a value happens to implement similarly named methods.

Protocol conversion remains a change of static view, not a runtime wrapper.

The same rules apply at every dynamic boundary, including:

- constructor payload validation;
- factory results;
- dynamically selected overload arguments and results;
- reflective invocation;
- host-to-Aloe and Aloe-to-host calls.

Trusted statically checked code may optimize redundant checks away. Its behavior must remain equivalent to having performed them.

### 8. Defensive constructor integrity

Normal Aloe code cannot forge a constructor identity, but the evaluator must still preserve the invariant that:

- the constructor belongs to the recorded family;
- payload arity matches its constructor declaration;
- every payload passes its substituted declared type;
- all generic arguments are resolved.

A malformed value must be rejected at the boundary that attempted to create or inject it. It must not survive until a later case expression or method send.

An exhaustive case form may therefore rely semantically on the family’s closed constructor set. The runtime can still defensively reject an impossible malformed value rather than choosing a default branch.

### 9. Built-ins and host values

This model does not require an immediate rewrite of built-ins.

Types such as `Bool` and `List` may eventually expose equivalent family-and-constructor descriptions, but the first implementation can preserve specialized representations behind the same observable rules.

Host interfaces and capabilities are different in kind:

- they remain opaque nominal values;
- they may possess meaningful identity or external state;
- they are not forced into algebraic payload representation merely for uniformity.

An algebraic family may contain such a capability, but doing so does not make the capability structurally inspectable or deeply immutable.

### 10. Alternatives I would reject

I would reject the following runtime models:

- **Constructor names as tags:** forgeable, collision-prone, and makes renaming affect type identity.
- **Each constructor as an independent class:** recreates the split ontology we are trying to remove.
- **Erasing generic arguments:** makes parameterless generic constructors and dynamic boundary checks unsound or ambiguous.
- **Reference equality for family values:** makes immutable products behave like objects with accidental allocation identity.
- **User-overridable equality for `check`:** makes trusted comparison depend on arbitrary behavior.
- **Protocol wrapper objects:** introduces allocation and identity changes merely from widening a static view.
- **Deep-freezing every payload:** incompatible with functions and host capabilities and unnecessary for stable algebraic structure.
- **Remembering the factory that produced a value:** leaks construction history that is irrelevant to the value’s meaning.
- **Letting raw printing invoke `show`:** removes the dependable diagnostic path.

### Resulting semantic nucleus

The compact rule is:

> An Aloe algebraic value is an immutable, nominally identified family instantiation containing one opaque constructor and its payload. Nominal identities govern type checks; structure governs kernel equality; names govern only source presentation and diagnostics.

That gives products, variants, protocols, generics, exhaustive elimination, and recursive data one coherent runtime foundation without exposing representation accidents.

The precise reflection surface is intentionally untouched here—that is Decision 8. The exact printed spelling remains for Decision 9.
