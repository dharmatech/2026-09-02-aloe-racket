## Decision 10: Static and implementation consequences

My recommendation is to treat this as a deliberate replacement of Aloe’s nominal core, implemented through a checked elaboration pipeline and delivered incrementally behind a temporary migration bridge.

The destination has one ontology only:

- family declarations;
- family type objects;
- representation constructors;
- immutable family values;
- whole-family and constructor-local messages;
- open protocols;
- internal constructor-set refinements.

The implementation must not permanently retain “class” as a parallel concept.

## 1. The implementation boundary

The current architecture independently type-checks an AST and then evaluates essentially the same unannotated AST. That is no longer sufficient.

In particular, the evaluator must know the type arguments selected by the checker for constructions such as:

```aloe
(Option None (type Int))
```

It must not attempt to rediscover `Int` from a payload that does not exist.

The revised pipeline should therefore be:

```text
source
  ↓
parsed source AST
  ↓
linked nominal declarations and opaque identities
  ↓
type checking and elaboration
  ↓
globally validated checked program
  ↓
evaluation
```

The checker produces an elaborated program containing the decisions required by runtime evaluation, including:

- resolved family and constructor identities;
- resolved static type arguments;
- case-clause constructor identities;
- static row obligations needed for result checking;
- refinement information needed only while checking.

Only a successfully checked and finalized program is evaluated.

The evaluator may still perform defensive checks at dynamic boundaries, but it no longer accepts unresolved construction semantics.

### Public API consequence

Conveniences such as `typecheck-source`, `eval-source`, and the driver can retain their existing broad roles.

Internally:

- `typecheck-source` may discard the elaborated program and return only its type;
- `eval-source` and the driver must evaluate the checked program;
- production evaluation should not accept an arbitrary raw parsed AST;
- tests that directly combine `read-program` with unchecked `eval-expr` should migrate to the checked driver or an explicitly internal testing helper.

This closes a boundary that generic parameterless constructors would otherwise make unsound.

## 2. Shared nominal descriptors

Within a program image, the checker, evaluator, and reflection system should refer to one linked graph of nominal descriptors.

The important identities are:

- protocol identity;
- family identity;
- constructor identity;
- dispatch-row identity.

A family descriptor contains the semantic metadata established by the design:

```text
family identity
name
type parameters
declared protocol conformances
ordered constructor descriptors
factory rows
whole-family rows
```

A constructor descriptor contains:

```text
constructor identity
owning family identity
selector label
ordered payload declarations
local rows
declaration position
```

A method-row descriptor contains its selector, generic parameters, parameter and result types, semantic role, body mode, and opaque row identity.

These are descriptors, not Aloe-visible reflective objects. Source programs continue to receive only the family type object and opaque `Signature` capabilities.

Using common descriptors prevents four independent systems from drifting:

- type lookup;
- runtime dispatch;
- protocol conformance;
- reflection.

The current host-interface descriptor already demonstrates the value of this arrangement.

## 3. Component consequences

| Component | Required change |
| --- | --- |
| Parser | Parse `define-family`, constructors, conformances, factories, local methods, per-constructor bodies, case clauses, and send type headers |
| Source AST | Represent family declarations, constructor declarations, cases, and explicit type arguments without prematurely desugaring away static facts |
| Linker/elaborator | Mint nominal identities, resolve declarations and types, and produce checked runtime annotations |
| Type checker | Track invariant family types and internal constructor-set refinements |
| Evaluator | Construct and dispatch through family and constructor descriptors |
| Protocol checker | Support multiple explicit whole-family conformances and row compatibility |
| Reflection | Reflect semantic rows, roles, and generic metadata while hiding multi-constructor representation |
| Printer/equality | Include family instantiation and constructor identity in structural behavior |
| Driver | Stage, validate, and commit a coherent program before evaluation |
| Examples and tests | Migrate from `define-class` and validate products, variants, recursion, protocols, Gel, and reflection |

Built-in primitives and host capabilities can retain specialized implementations behind the same boundary.

## 4. Static family types and refinements

The checker should keep the nominal type and constructor knowledge conceptually separate.

The base type is:

```text
F A...
```

An internal refinement adds a possible-constructor set:

```text
base type:              F A...
possible constructors: {C1, C2, ...}
```

An implementation may represent this with a dedicated internal refined-type wrapper or equivalent flow metadata. It should not merely add constructor sets to ordinary nominal equality, because that invites accidental subtyping behavior.

Central operations should include the equivalents of:

- obtain the base nominal type;
- obtain the currently possible constructors;
- refine by intersection;
- subtract handled constructors;
- union branch refinements;
- widen to the base family;
- forget refinement during protocol conversion or storage.

`type->datum`, diagnostics for ordinary annotations, and the public type grammar expose only the base type.

### Refinement production

The checker introduces refinements from:

- direct representation-constructor sends;
- exhaustive case branches;
- per-constructor family bodies;
- immutable direct aliases.

### Refinement preservation

A direct immutable `define` or `let` alias may retain the outer refinement of its value.

The current parser immediately lowers `let` to an `fn`/`call` combination. That loses the distinction between an immutable alias and an ordinary function boundary. The parser should therefore retain a source-level `let` node, or equivalent provenance, through checking.

Its runtime semantics remain exactly the existing desugaring:

```aloe
(let ((x value)) body)
```

is operationally equivalent to calling an `fn`. Refinement preservation is a checker fact granted to the source alias, not general function-argument refinement.

### Refinement loss

Refinement is normally forgotten through:

- declared method and factory results;
- protocol conversion;
- general function parameters and results;
- generic storage such as `List`;
- payload positions declared with an unrefined family type;
- reflective unwrapping.

This must be tested explicitly so refinements do not accidentally become deep types.

## 5. Declaration linking

A family is linked in phases.

### Phase one: header and identities

Before checking payload types or bodies:

- bind the family name;
- mint its opaque family identity;
- create its family type object;
- bind its type parameters;
- register all constructor names and opaque constructor identities.

This permits direct regular self-reference in payload types.

### Phase two: representation

Resolve:

- constructor payload types;
- accessor rows;
- local signatures;
- factory signatures;
- whole-family signatures;
- conformance names.

At this stage enforce:

- a nonempty constructor set;
- unique constructor selectors;
- reserved selector rules;
- unique payload names per constructor;
- family/local selector partitioning;
- exact row uniqueness.

### Phase three: bodies

Install all signatures belonging to the declaration before checking its bodies. This preserves recursive and mutually referential methods within one declaration.

Then check:

- local bodies with singleton-refined `self`;
- uniform family bodies with unrefined `self`;
- per-constructor bodies with appropriately refined `self`;
- factories with the family type object as `self`.

### Direct recursion rule

While resolving payloads, the current family may refer to itself only at full arity with the same parameters in the same order.

Previously declared families remain available. General forward and mutually recursive family groups remain rejected.

## 6. Additive extensions and finalization

`define-methods` additions should be staged rather than mutating a committed descriptor before validation.

Within one extension form:

1. resolve every proposed row signature;
2. reject forbidden selectors and exact replacements;
3. install the proposed signatures into a staging view so their bodies may call one another;
4. check all bodies;
5. run ambiguity and return-coherence checks;
6. commit the rows only if the complete extension is valid.

Factory additions follow the same process on the type-object surface.

Extensions never reopen the constructor set, local tables, per-constructor body tables, or conformance list.

### Whole-program validation

After a complete source unit and its transitive loads have been checked, validate:

- every declared protocol conformance;
- every per-constructor body table;
- every overload set;
- dynamic-overload return coherence;
- selector classification;
- unresolved type variables;
- extension ownership.

Methods supplied by later `define-methods` forms in that same source unit participate in conformance.

For an interactive REPL, each submitted datum is its own transaction. A family declaration claiming a protocol must be coherent when that transaction commits. A file containing a declaration followed by required extensions is checked as one larger transaction.

A failed declaration or extension must not leave a partially modified checker environment.

Ordinary runtime effects that occur after successful checking are not retroactively rolled back.

## 7. Generic inference and elaboration

The existing local unification machinery can evolve rather than being replaced by a full Hindley–Milner system.

For each constructor or factory send, the checker creates fresh variables and gathers constraints from:

- the optional explicit `(type ...)` header;
- the expected exact family result;
- payload or factory arguments;
- the enclosing expression;
- sibling case branches where their results must agree.

Constraint collection must not commit to a result based on the first branch encountered. Branch order must not affect inferred types.

### Explicit arguments

The checker validates the complete explicit list against:

- family parameter count;
- row-level parameter count;
- source type well-formedness;
- payload and expected-type constraints.

Explicit arguments are copied into the checked send. They are not runtime argument expressions.

### Checking-unit boundaries

Unresolved type variables may exist temporarily inside constraint solving. They may not remain when finishing:

- a top-level expression or definition;
- a method or factory body;
- an explicitly typed function body;
- a complete program transaction.

Declared family and method type parameters are not unresolved variables; they are valid bound parameters.

A context-free parameterless construction such as:

```aloe
(Option None)
```

therefore fails at its checking-unit boundary unless surrounding constraints determine `T`.

### Runtime consequence

Every checked constructor send carries its resolved family arguments. The evaluator uses those arguments directly when constructing the value.

Runtime payload inference is removed rather than retained as a fallback.

## 8. Static message lookup

Static lookup becomes receiver-sensitive in a precise way.

### Family type object

Available rows:

- representation constructors;
- factories.

A constructor result is singleton-refined. A factory result has only its declared type.

### Unrefined family value

Available rows:

- whole-family messages.

### Singleton-refined family value

Available rows:

- whole-family messages;
- the selected constructor’s local methods and payload accessors.

A one-constructor family is inherently singleton-refined.

### Protocol value

Available rows:

- protocol signatures only.

Converting a refined family value to a protocol forgets its constructor set.

### Broader non-singleton refinement

If a case default leaves several constructors possible, only whole-family messages are available. Repeated local selector names are never intersected into an implicit common surface.

## 9. Exhaustive case checking

The parser records source labels and binders. The checker resolves each constructor label relative to the scrutinee’s family and elaborates it to its opaque constructor identity.

Runtime case dispatch should not compare names.

The checker:

1. checks the scrutinee once;
2. extracts its concrete family and possible constructor set `S`;
3. resolves every explicit clause to a constructor identity;
4. rejects duplicates, unknown cases, and cases impossible under `S`;
5. validates exact payload-binder arity;
6. computes the residual set for `else`;
7. checks coverage;
8. checks every reachable branch result without branch-order bias;
9. records the resolved constructor identities in the checked case.

Each explicit branch receives:

- payload types after substituting family arguments;
- an optional whole binding with singleton refinement.

A default whole binding receives the residual refinement.

The evaluator:

- evaluates the scrutinee exactly once;
- compares its opaque constructor identity with the checked clause identities;
- binds the existing immutable payload values;
- evaluates exactly one body.

A malformed foreign value that violates the closed family descriptor is rejected rather than routed through `else`.

## 10. Branch result checking

With an expected type, every reachable branch is checked against it.

Without an expected type:

- exact ordinary types must unify;
- same-family generic arguments unify invariantly;
- outer family refinements are unioned;
- distinct conforming families do not automatically invent a protocol result;
- an `else` branch participates like every explicit branch.

The implementation should make this join operation explicit rather than reuse a left-biased “first branch wins” helper.

This rule is important for:

```aloe
(if condition
    (Option None)
    (Option Some 1))
```

and:

```aloe
(result case
  (Ok (value) ...)
  (Error (message) ...))
```

## 11. Protocol conformance and overload coherence

A family stores a list of exact protocol identities.

For every required protocol row, finalization must find a whole-family row whose:

- parameters accept the complete protocol parameter domain;
- result is usable as the protocol result.

Constructor rows, factories, payload accessors, and local rows are not candidates.

The compatibility calculation must use the same central type relation used by:

- ordinary calls;
- runtime argument validation;
- `Signature.accepts?`;
- reflective invocation;
- host boundaries.

No name-based duplicate relation should be introduced.

### Dynamic overload coherence

For every pair of runtime-overlapping overload rows where one may be selected in place of a statically broader row, the narrower row’s result must be usable as the broader row’s result.

This check occurs across declaration-owned and extension-owned rows after the complete overload set is known.

MPL’s useful concrete overload dispatch is preserved, but an extension cannot introduce a result that invalidates the caller’s static promise.

## 12. Runtime family values

The current runtime pair of `class-value` and `instance-value` is replaced conceptually by:

```text
family type object / family descriptor

family data value:
  family descriptor
  resolved type arguments
  constructor descriptor
  immutable payload vector
```

The value does not contain method closures or factory provenance.

Dispatch consults descriptor tables:

- constructor/factory table for the type object;
- whole-family table for family instances;
- local table only for the actual constructor when statically permitted;
- constructor-indexed body map for a per-constructor family row.

The descriptor may be append-only for permitted method extensions. Its constructor set and conformance claims are fixed when the family declaration commits.

## 13. Runtime checks, equality, and printing

One centralized runtime type relation should handle:

- exact family identity;
- invariant family arguments;
- explicit protocol conformance;
- refined constructor membership;
- primitives, functions, lists, and host interfaces.

Direct sends, reflective invocation, factories, and host crossings should call that relation rather than maintain variants.

Kernel family equality becomes:

```text
same family identity
and same resolved type arguments
and same constructor identity
and recursively equal payloads
```

This corrects the current class-instance comparison, which does not need to distinguish constructors and does not include generic arguments.

The structural printer derives its output from the family and constructor descriptors:

```text
#<Point 1 2>
#<Option.None>
#<Option.Some 1>
```

Existing ad hoc user-family printer cases should disappear. Domain presentation remains in ordinary `show` methods.

## 14. Reflection implementation

A `Signature` should retain an opaque row descriptor rather than rely primarily on an integer position in a flattened table. Row indices become fragile once constructors, factories, whole-family rows, local rows, and extensions occupy different surfaces.

Its hidden authority includes:

- exact owner identity;
- exact receiver instantiation where relevant;
- exact row identity;
- generic row description;
- semantic role.

`Mirror` constructs its visible surface according to Decision 8:

- multi-constructor instance: whole-family rows;
- one-constructor instance: whole-family and sole local rows;
- family type object: constructor and factory rows;
- primitive and host receivers: existing public rows.

`role` and `type-params` are derived directly from the row descriptor.

Reflective invocation uses the descriptor itself and never performs selector lookup again.

Multi-constructor local rows must be filtered at the point where signatures are created, not merely rejected after exposing their existence.

## 15. Built-ins remain specialized

This implementation does not require rewriting:

- `Bool` as a two-constructor source family;
- `List` as `Empty`/`Cons`;
- primitive numbers or strings;
- `Symbol`;
- `Mirror` and `Signature`;
- host capabilities.

They should use adapters into the common runtime type and reflection relations where necessary.

A later application may justify expressing a built-in through the family machinery, but this design does not use that as an implementation prerequisite or success criterion.

## 16. Compatibility boundary

The final language deliberately rejects:

- `define-class`;
- the positional protocol after a class header;
- family-level `fields`;
- implicitly generated `new`;
- permanent class/family aliases.

All repository Aloe source, examples, fixtures, and tests must eventually use `define-family`.

### Temporary migration bridge

A temporary, explicitly non-normative parser bridge is justified while the suite is migrated.

During implementation only, an old declaration:

```aloe
(define-class (Point T) Math
  (fields
    (x T)
    (y T))
  (methods
    ...))
```

may lower internally to the equivalent:

```aloe
(define-family (Point T)
  (conforms Math)
  (constructors
    (new
      (fields
        (x T)
        (y T))))
  (methods
    ...))
```

This bridge provides three benefits:

- existing tests remain green during internal replacement;
- one runtime ontology is exercised immediately;
- application migration can occur after the core semantics stabilize.

The bridge is not documented as language syntax and must have an explicit removal checkpoint. The final suite must include rejection tests for `define-class`.

This is development sequencing, not a source-compatibility promise.

### Racket-facing compatibility

Public driver conveniences should remain when inexpensive. Internal Racket structs such as `class-info`, `class-value`, `instance-value`, and integer-indexed reflected rows are implementation details and should not constrain the redesign.

The guarded host-interface API remains a real boundary and should be adapted rather than bypassed.

## 17. Transactional checking

The current checker mutates its environment as it processes declarations. Families, conformances, and extensions add enough global invariants that failed checks must not poison a live driver.

A source load should operate against a staging environment:

1. link declarations and extensions;
2. check all expressions and bodies;
3. run final coherence and conformance validation;
4. commit the static descriptors;
5. evaluate the checked program into the corresponding runtime environment.

A REPL datum follows the same smaller transaction.

This does not require transactional rollback of arbitrary host effects because no evaluation begins until static commit. Runtime failures after evaluation begins retain the ordinary current behavior.

## 18. Validation applications

The design should not be considered complete after isolated `Option` tests.

| Program | What it validates |
| --- | --- |
| `Point` | One-constructor products, fields, construction, equality, printing, and local reflection |
| Boids | Nested generics, immutable products, lists, numeric messages, and application-scale migration |
| MPL | Open protocols, additive family methods, overload specificity, return coherence, and `show` |
| `Option` | Nullary and unary generic constructors, inference, explicit type arguments, and exhaustive case |
| `Result` | Two independent generic parameters and constraints gathered across alternatives |
| `Tree` | Direct regular recursion, nested family payloads, recursive methods, and nested elimination |
| Filesystem model | Domain `Other` constructor, case-local capabilities, defaults, and closed representation |
| Gel | Reflection remains useful while application state moves from sentinel lists and booleans to closed families |
| Term/host tests | Exact nominal host identity and guarded reflective invocation remain intact |

### Gel acceptance test

Gel is especially important because it exercises both halves of the design.

Its empty-or-singleton `(List GelRow)` pending representation should be replaced with a real closed representation, initially at least `Option GelRow`.

A stronger subsequent cleanup may represent idle, pending-pick, pending-integer, and quit states with an application-specific family. That refactor should preserve existing key behavior and emitted text byte-for-byte unless a separate UI decision is made.

Gel must continue to use:

- `Mirror`;
- exact `Signature` rows;
- `accepts?`;
- reflective invocation;
- raw subject presentation.

The ADT design succeeds only if this becomes clearer without weakening reflection boundaries.

## 19. Required negative tests

The implementation needs tests for failures as seriously as successful examples.

Declaration diagnostics:

- zero constructors;
- duplicate constructors;
- reserved `case` or `else` constructors;
- constructor/factory collision;
- family/local selector collision;
- payload/local collision;
- duplicate exact overload;
- incomplete `per-constructor` table.

Construction diagnostics:

- wrong payload arity;
- payload type mismatch;
- explicit type-argument arity mismatch;
- conflicting explicit and inferred types;
- unresolved nullary constructor;
- invariant family mismatch.

Case diagnostics:

- non-family scrutinee;
- protocol scrutinee;
- missing constructor;
- duplicate constructor;
- unknown constructor;
- impossible constructor under refinement;
- wrong payload-binder arity;
- misplaced or unreachable `else`;
- incompatible branch results;
- proof that unselected branches are not evaluated;
- proof that the scrutinee is evaluated once.

Refinement diagnostics:

- local send on an unrefined multi-constructor value;
- local send after factory return;
- local send after protocol conversion;
- local send after generic storage;
- preserved direct-alias refinement;
- union and widening after branch joins.

Protocol diagnostics:

- per-constructor conformance attempt;
- local method offered for a protocol requirement;
- missing whole-family method;
- incompatible parameter domain;
- incompatible result;
- nonuniform generic conformance;
- incoherent narrower overload result.

Recursion diagnostics:

- wrong self-recursive argument;
- reordered parameters;
- nonregular recursion;
- mutual forward recursion;
- unresolved external family.

Reflection diagnostics:

- multi-constructor local rows absent;
- constructor and factory roles correct;
- exact generic ownership enforced;
- same-named unrelated owners rejected;
- user construction of signatures rejected;
- selector symbols cannot invoke;
- constructor names and raw strings produce no refinement.

## 20. Safe checkpoint sequence

The repository is currently complete through Checkpoint 88. I recommend the following provisional sequence. A checkpoint may be subdivided if its implementation diff becomes difficult to review, but the dependency order should remain.

### Checkpoint 89: Ratify the language design

- Rewrite the approved design into normative `SPEC.md` language.
- Add the implementation sequence to `CHECKPOINTS.md`.
- Produce the separate self-contained implementation handoff.
- Do not change runtime behavior.

This checkpoint is required before implementing the new `case` special form, satisfying the repository rule that special forms must first exist in the specification.

### Checkpoint 90: Checked evaluation seam

- Introduce an internal checked/elaborated expression result.
- Route the driver and source evaluation helpers through it.
- Preserve all current Aloe behavior.
- Remove production dependence on evaluating unchecked parsed sends.
- Add tests showing failed checking prevents evaluation and environment commit.

### Checkpoint 91: Nominal descriptor nucleus

- Introduce shared family, constructor, protocol, and row descriptors.
- Represent every legacy class internally as a one-constructor family named `new`.
- Preserve current syntax through the temporary bridge.
- Keep the entire existing suite green.
- Do not expose multi-constructor source syntax yet if the slice becomes too large.

### Checkpoint 92: One-constructor `define-family`

- Accept the new declaration grammar for product families.
- Support uniform methods and explicit `new` constructors.
- Demonstrate equivalence with `Point`.
- Retain temporary `define-class` lowering.
- Reject malformed family sections and constructor collisions.

### Checkpoint 93: Multiple representation constructors

- Support multiple named constructors and immutable payload vectors.
- Implement opaque constructor identity.
- Implement family-and-constructor-aware equality and raw printing.
- Begin with a non-generic closed family.
- Keep multi-constructor local reflection unavailable.

### Checkpoint 94: Explicit type arguments and generic constructors

- Parse send `(type ...)` headers.
- Elaborate resolved type arguments into checked sends.
- Support generic `Some`, `None`, `Ok`, and `Error`.
- Reject unresolved generic arguments at checking boundaries.
- Test invariant instantiations and branch-order-independent constraints.

### Checkpoint 95: Constructor refinements and local surfaces

- Produce singleton refinements from direct construction.
- Preserve direct immutable aliases.
- Add payload accessors and constructor-local methods.
- Restrict local lookup to singleton knowledge.
- Implement widening through protocols, storage, and ordinary declared results.

### Checkpoint 96: Exhaustive explicit case

- Implement receiver-anchored `case` with explicit constructor clauses.
- Evaluate the scrutinee once and one branch lazily.

- Diagnose missing, duplicate, unknown, impossible, and wrong-arity cases.

### Checkpoint 97: Default clauses and branch joins

- Add final `else` with residual refinement.
- Reject empty residual defaults.
- Implement symmetric branch-result constraint gathering.
- Union outer constructor refinements.
- Keep protocol results explicit rather than inventing a least upper bound.

### Checkpoint 98: Whole-family body modes

- Add `per-constructor` method bodies.
- Enforce exact constructor coverage.
- Dispatch through the actual constructor while reflecting one family row.
- Seal family/local selector partitions and return coherence for local additions.

### Checkpoint 99: Factories and additive extensions

- Add declaration-level factories.
- Extend `define-methods` with the `factories` section.
- Give factory bodies the family type object as `self`.
- Keep factory results at their declared static type.
- Stage extension rows atomically and forbid replacement.

### Checkpoint 100: Multiple protocols and global coherence

- Implement `(conforms P ...)`.
- Enforce whole-family conformance.
- Implement parameter/result compatibility.
- Validate uniform generic conformance.
- Run global overload ambiguity and return-coherence checks.
- Revalidate MPL’s concrete dynamic-overload behavior.

### Checkpoint 101: Direct regular recursion

- Register family and constructor headers before payload resolution.
- Accept regular self-recursive payloads.
- Reject nonregular and mutually recursive groups.
- Validate recursive `Tree` construction, methods, equality, printing, and case.

### Checkpoint 102: Family-aware reflection

- Add signature `role` and `type-params`.
- Reflect constructors and factories from type objects.
- Reflect only whole-family rows from multi-constructor instances.
- Preserve one-constructor field and local reflection.
- Replace fragile row indices with exact row descriptors.
- Re-run all Gel and host-reflection tests.

### Checkpoint 103: Repository migration and bridge removal

- Convert every Aloe source file, example, fixture, and test to `define-family`.
- Move positional protocol claims to `(conforms ...)`.
- Preserve existing `Point`, Boids, MPL, Gel, and Term behavior.
- Remove the temporary `define-class` parser bridge.
- Add explicit rejection tests for legacy syntax.

### Checkpoint 104: Canonical `Option` and `Result`

- Add small, readable application examples.
- Exercise contextual and explicit nullary construction.

- Avoid prematurely making them magical built-ins.

### Checkpoint 105: Gel state validation

- Replace the empty-or-singleton pending list with `Option`.
- Introduce an application-specific state family if it materially simplifies the remaining Boolean state.

### Checkpoint 106: Filesystem and final seal

- Validate a closed filesystem classification family with an explicit `Other`.
- Exercise local capability access and exhaustive external consumers.
- Run the complete regression suite and application runners.
- Finalize normative documentation and implementation notes.
- Review implementation size and remove transitional duplication.
- Leave built-in algebraic rewrites explicitly deferred.

## 21. Checkpoint discipline

Every implementation checkpoint must:

- include its tests in the same change;
- run the full existing suite, not only its new test;
- leave unsupported later syntax rejected clearly;
- avoid temporary behavior that contradicts an approved semantic rule;
- remain independently reviewable;
- stop when green.

In particular, an intermediate implementation must not:

- infer runtime generic arguments from payloads;
- use constructor names as runtime tags;
- expose multi-constructor local rows through reflection;
- accept partial case analysis;
- silently treat repeated local selectors as family messages;
- fall back to structural protocol conformance.

When a later feature is unavailable, the implementation should reject it rather than approximate it unsafely.

## 22. Definition of completion

The unified nominal algebraic model is complete when:

- `SPEC.md` contains the normative design;
- `define-family` is the sole user nominal declaration;
- no public parser path accepts `define-class`;
- products, variants, factories, local operations, family operations, protocols, generics, case analysis, recursion, equality, printing, and reflection obey Decisions 1–9;
- the evaluator receives all checked construction type arguments;
- the entire historical checkpoint suite is green after migration;
- Boids, MPL, Gel, Term, `Option`, `Result`, `Tree`, and the filesystem model run;
- the reflection and host boundaries retain exact nominal ownership;
- no temporary dual class/family runtime remains;
- built-in rewrites remain optional rather than hidden unfinished work.

## 23. Strategies I would reject

I would reject:

- **A flag-day rewrite:** too many independent regressions would become indistinguishable.
- **Permanent dual class and family runtimes:** recreates the ontology split internally.
- **Lowering each constructor to an unrelated class:** cannot support correct nominal identity or exhaustive families.
- **Implementing case through names or reflection:** violates Decisions 4, 7, and 8.
- **Runtime reconstruction of generic arguments:** fails for nullary constructors.
- **Continuing to evaluate unannotated ASTs:** loses checked construction decisions.
- **Migrating Gel before reflection and case semantics stabilize:** obscures core failures with application churn.
- **Rewriting `List`, `Bool`, and all primitives immediately:** greatly expands risk without validating the user-defined model.
- **Keeping `define-class` indefinitely for compatibility:** leaves two public ontologies.
- **Adding general subtyping, GADTs, mutual recursion, or a first-class type universe during implementation:** expands beyond the approved design.
- **Treating documentation as a final cleanup:** the special form and compatibility boundary must be normative before implementation.

## Decision 10 nucleus

The implementation should introduce one linked nominal descriptor model, make type checking produce the runtime decisions evaluation requires, and migrate the repository incrementally through a temporary legacy parser bridge that is removed before completion.

The order is:

```text
specification
→ checked elaboration
→ one-constructor family core
→ multiple constructors
→ generics and refinements
→ exhaustive case
→ family behavior and factories
→ protocols and recursion
→ reflection
→ repository migration
→ application validation
```
