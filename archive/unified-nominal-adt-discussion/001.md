# What exactly does one unified nominal algebraic declaration mean in Aloe?

A declaration introduces one closed nominal family of immutable values, together with the value-level object used to construct and organize them. A present-day class is exactly the special case whose family contains one representation constructor.

The recommended nucleus is:

> One nominal family type, one ordinary type object, one or more constructor identities, and static case refinements—not a hierarchy of case classes.

## Semantic nucleus

| Entity | Meaning |
|---|---|
| Declaration | Creates one nominal identity, its type constructor, one type object, a finite nonempty set of representation constructors, message surfaces, and optional protocol conformance. |
| Nominal type | The shared static type of every value in the family, such as `Point T`, `Option T`, or `EntryKind`. Identity comes from the declaration, not its printed name or structure. |
| Type object | The ordinary receiver denoted by the declaration’s value name. It owns constructor messages and ordinary type-object methods such as factories. It is not itself a value of the family. |
| Representation constructor | A distinguished type-object message tied to exactly one declared case. It creates that case directly from its declared payload and contributes one member to the exhaustiveness set. |
| Factory message | An ordinary method on the type object. It may compute, validate, delegate to constructors, or return an existing value. It introduces no case and has no role in exhaustiveness. |
| Runtime value | Its instantiated nominal family identity, constructor identity, immutable payload, and runtime type arguments needed by checked reflection. |
| Constructor identity | An opaque nominal token owned by one declaration. Its selector/name is a label, not the identity itself. Same-named constructors in different families are unrelated. |
| Whole-family surface | Messages guaranteed for every representation constructor. They are available whenever the receiver is known only as the family type. |
| Refined case surface | Payload selectors and case-local messages available once the checker knows the constructor identity. It extends the whole-family surface without creating another nominal type. |
| Protocol conformance | An open behavioral claim made by the whole nominal family. Protocol dispatch remains ordinary runtime message dispatch on the actual value. |

### Static case knowledge

A concrete family type may carry an internal constructor-set refinement:

- An unrefined `Option T` may be `None` or `Some`.
- A freshly constructed `Some` has the same nominal type `Option T`, with the static fact that its constructor is `Some`.
- An exhaustive branch narrows that fact to one constructor.
- Widening to the family type forgets the fact.
- Refinements are not source-written types, new runtime wrappers, subclasses, or protocol implementations.

This gives payload precision and editor discovery without introducing types such as `Some T` and a subtype relation between `Some T` and `Option T`.

For a one-constructor family, refinement is tautological: every value is already known to have that constructor. Consequently, `Point` fields and ordinary messages remain directly available. Products do not acquire variant ceremony merely because the underlying model is general.

## Messages remain one universe

Every constructed value remains an ordinary receiver.

A declaration associates dispatch rows with the family and, where applicable, with constructor identities. Static refinement determines which selectors the checker and editor may expose; it does not introduce another evaluation mechanism. Protocols remain contracts rather than method tables.

The precise choice between one shared family method body and per-constructor bodies belongs to Decision 3. The ontology only requires:

- Family messages to be valid for every constructor.
- Case messages to require sufficient constructor knowledge.
- Runtime dispatch to remain the ordinary receiver-first rule.

A refined concrete value exposes:

1. Whole-family messages.
2. Its constructor-specific payload selectors and messages.
3. Protocol conversion when the whole family conforms.

A value viewed through a protocol exposes the protocol’s selectors. Protocol conversion intentionally forgets closed constructor knowledge.

## Constructors and factories are materially different

A representation constructor is not merely a method that happens to return the family type. It is part of the family’s declared representation:

- It has one constructor identity.
- Its payload determines the stored fields.
- Successful invocation produces that constructor, not an arbitrary result.
- Adding or removing it changes exhaustive consumers.

A factory has an ordinary method body:

- It may select among constructors.
- It may return an existing value.
- It may be overloaded like another type-object method.
- Adding or removing it changes the construction API but not the closed family.

The smallest nucleus does not require constructors to become standalone function values. They are discoverable type-object messages. Whether constructor rows can later be extracted as first-class reflective handles belongs to Decision 2.

## What happens to “class”?

There is no remaining semantic category corresponding to a user-defined class.

Today’s components translate directly:

- Class identity becomes nominal declaration identity.
- Class object becomes type object.
- Generated `new` becomes the sole representation-constructor message of a one-constructor family.
- Instance class pointer becomes family identity plus constructor identity.
- Fields become the constructor payload.
- Class methods become family or constructor-local messages.

“Class” might survive temporarily as surface terminology or syntax, but it would not describe a second object model.

Primitive values, functions, built-in lists, mirrors, signatures, and host capabilities need not immediately be reimplemented using user declarations. The semantic model should eventually be able to explain algebraic built-ins such as `Bool` and `List`, but the first implementation need not erase their kernel representations.

## Consequences for the pressure cases

- `Point T` has one constructor with `x : T` and `y : T`. Its fields and messages are immediately discoverable because there is only one possible constructor.
- `Option T` has one family type and two constructor identities. `Some` reveals a `T` payload after refinement; `None` does not pretend to have one.
- Every filesystem alternative remains an `EntryKind`, so `(List EntryKind)` is homogeneous. Refinement reveals `FileFacts`, `DirectoryFacts`, and the other precise payloads.
- `Tree T` can refer recursively to its own family type in a constructor payload. The ontology permits this; recursive well-formedness is Decision 5.
- Gel can replace its empty-or-singleton pending list with `Option GelRow`, and later represent mutually exclusive state using one closed `GelMode` family.
- MPL’s `Math` remains an open protocol. Future users add new nominal families conforming to `Math`; they do not edit or extend a closed `MathExpr` constructor set. A closed algebraic family may conform to `Math` as a whole.

## Identity, equality, and reflection consequences

The current implementation already uses exact declaration identity for instance typing, dispatch ownership, and structural equality. The generalization adds constructor identity to that account.

The expected value-equality nucleus is:

1. Same instantiated nominal family.
2. Same constructor identity.
3. Recursively equal payloads.

Exact generic-runtime and user-facing equality rules remain for Decision 7.

Reflection should eventually observe both family and constructor metadata, but constructor identity must not become the ordinary discrimination API. `Mirror` remains observational, and `Signature` rows remain exactly owned. The existing same-name-but-distinct nominal ownership behavior is the right precedent.

## Smallest credible alternatives

1. **Distinct nominal case subtypes.** Each case would be its own type beneath a sealed family type. This makes cases directly nameable in annotations and overloads, but introduces subtyping, a sealed hierarchy, conversion rules, and more complicated collection, equality, overload, and reflection semantics. It recreates “classes plus a sum wrapper” rather than yielding one value model.

2. **Constructor identities without refined receiver views.** All values share the family type, and elimination only binds raw payloads. This has a slightly smaller checker but makes case-local messages undiscoverable and pushes behavior into helper objects or family-wide methods. It also makes the one-constructor product case need special treatment.

3. **Source-nameable refinement types.** Keep the recommended runtime model but expose types resembling `Option.Some T`. This could later support case-specific annotations, but it expands the type grammar and raises subtype, variance, overload, and protocol questions before an application requires them.

The recommended internal-refinement model is the smallest one that preserves one-constructor ergonomics, precise case payloads, post-refinement discovery, homogeneous family collections, and one dispatch universe.

## Deferred—not silently decided

The nucleus deliberately leaves these for their assigned decisions:

- Constructor lookup, inference, expected types, and first-class status.
- Shared versus per-constructor method bodies and dispatch precedence.
- Exhaustive elimination syntax and wildcard policy.
- Refinement joins, generic empty constructors, variance, and recursion checks.
- Multiple protocols and whether case-only conformance is ever worthwhile.
- Exact printing, equality, runtime checks, and reflection vocabulary.
- Applicative versus generative identity for future nested declarations and modules.

The review point is therefore narrow: approve or revise **one family type + one type object + nominal constructor identities + internal case refinements + whole-family protocol conformance**.
