# Decision 4: How should Aloe eliminate a closed family exhaustively?

The recommended design is:

> Add one receiver-anchored exhaustive case special form. It evaluates its receiver once, selects by constructor identity, introduces precisely typed payload and refined-value bindings, and evaluates exactly one branch.

Illustrating only the semantic shape—not choosing final syntax:

```alo
(option case
  (none ...)
  (some (value) ...))
```

Although it resembles a send, the branches are syntax rather than evaluated arguments. This is the smallest design that preserves receiver-first reading while supporting lexical bindings, laziness, refinement, and static exhaustiveness.

## 1. Why this should be a special form

An exhaustive case operation needs to do four things ordinary sends cannot naturally do:

- Treat constructor labels as literals rather than evaluated values.
- Introduce branch-local payload bindings.
- Refine the receiver differently in each branch.
- Avoid evaluating unselected branches.

Forcing those jobs through ordinary messages would require generated handler-function signatures, explicit thunks, constructor ordering, or first-class constructor objects. It would enlarge several existing mechanisms merely to avoid one focused special form.

The new form complements messages:

- Operations owned by a family can use Decision 3’s case-complete message bodies.
- External consumers can eliminate a family without adding methods to it.
- Branch bodies remain ordinary Aloe expressions and sends.
- The scrutinee remains visually and semantically first.

One eliminator marker—illustrated here as `case`—would be reserved rather than available as an ordinary selector. Its final spelling and exact parentheses remain Decision 9.

## 2. What may be eliminated

Exhaustive elimination requires a statically known, concrete nominal family.

Valid subjects include:

- `Option T`
- `Result T E`
- `Tree T`
- `EntryKind`
- A value already refined to a subset or singleton constructor set

It is not available on:

- An open protocol such as `Math`
- An unconstrained type parameter
- An arbitrary `Mirror`
- A type object
- A value whose nominal family cannot be determined statically

Protocols are intentionally open: the checker cannot enumerate all present and future conforming declarations. Treating current protocol implementations as exhaustive would destroy MPL’s downstream openness.

A mirror may unwrap a subject through an expected concrete type and runtime check. Once the result is statically a concrete family value, ordinary case elimination may apply. Reflection itself does not perform the discrimination.

## 3. Coverage is relative to the scrutinee’s possible constructors

Let:

- `S` be the constructor identities the checker considers possible for the scrutinee.
- `E` be the constructor identities named by explicit branches.

For an unrefined `Option T`:

```text
S = {None, Some}
```

For a value already refined to `Some`:

```text
S = {Some}
```

Without a default branch, exhaustive case requires:

```text
E = S
```

This makes refinement meaningful. Eliminating a known `Some` requires only the `Some` branch; adding a `None` branch is unreachable.

Constructor labels are resolved relative to the scrutinee’s nominal declaration. They are literal labels, not environment variables or globally unique names.

## 4. Explicit branches

Each explicit constructor branch semantically receives:

1. The original value refined to that constructor.
2. One payload binding for every constructor payload slot.
3. An ordinary Aloe expression as its body.

For `Some T`, the branch environment contains:

```text
whole value : Option T, refined to Some
payload     : T
```

For `Branch T`, it contains:

```text
whole value : Tree T, refined to Branch
left        : Tree T
right       : Tree T
```

The final syntax may allow the programmer to omit the whole-value binder when only payloads are needed. Semantically, however, the refined value always exists.

The refined whole-value binding is important because payload bindings alone would not expose Decision 3’s case-local message surface. Inside a `RegularFile` branch, the programmer can both:

- Use the precisely typed `FileFacts` payload.
- Send regular-file-local messages to the refined `EntryKind` value.

Payload binders correspond to the constructor’s declared payload slots in order. A branch must account for the exact payload arity; partial and nested patterns are not part of the initial design.

Bindings are lexical, immutable, and visible only in that branch. Duplicate binders within a clause are errors.

## 5. Evaluation

Runtime evaluation is small and deterministic:

1. Evaluate the scrutinee exactly once.
2. Read its constructor identity.
3. Select the corresponding explicit branch, or the default branch if present.
4. Bind the whole value and payload values.
5. Evaluate only the selected branch body.
6. Return that body’s result.

Constructor selection uses opaque constructor identity, never:

- Printed constructor names
- Symbols or strings
- Structural payload shape
- A user-defined equality method
- Reflective selector lookup

A defensive runtime may report a non-exhaustive-case failure for malformed unchecked input, but a successfully checked Aloe program cannot reach it.

## 6. Exhaustiveness diagnostics

The checker should distinguish the following errors.

### Missing constructors

Without a default:

```text
non-exhaustive case for Option Int;
missing constructor: Some
```

For several omissions, list them in declaration order.

### Duplicate constructor

```text
duplicate case branch: Some
```

Branches do not fall through, so a repeated constructor can never be useful.

### Unknown constructor

```text
Option has no constructor: Error
```

Because labels resolve within the scrutinee family, a same-named constructor from another declaration does not match.

### Impossible constructor

If the scrutinee is already refined:

```text
unreachable case branch: None;
the receiver is known to be Some
```

This is distinct from an unknown constructor: `None` belongs to the family but is not possible here.

### Payload-arity mismatch

```text
constructor Some has 1 payload value;
branch binds 2
```

### Unreachable default

A default branch is unreachable when explicit branches already cover every constructor currently possible.

### Branch-result mismatch

The diagnostic should identify the constructor branches and their incompatible result types rather than reporting an anonymous unification failure.

## 7. Default handling

A final default branch should be permitted, but it is an explicit opt-out from constructor-by-constructor evolution checking.

With a default:

```text
E ⊂ S
default covers S − E
```

The default must be final and must cover at least one currently possible constructor. Otherwise it is unreachable.

The default branch:

- May bind the whole residual family value.
- Receives no constructor-specific payload bindings.
- Carries the residual constructor-set refinement.
- May use family messages.
- May use case-local messages only if the residual set happens to be a singleton.

If a later constructor is added, it automatically enters the default branch. Therefore no missing-constructor diagnostic is produced at that case site.

This is intentional. A default means:

> Handle all remaining and future alternatives according to this common policy.

It should not be mistaken for an explicit domain case. In the filesystem example, `Other OtherFacts` remains a declared constructor with a typed payload. It is not replaced by a default branch.

Aloe should not permit silently non-exhaustive case expressions. Every case must use complete explicit coverage or one final default.

## 8. Duplicate and unreachable detection remains simple

Because the first facility supports only flat constructor branches, overlap checking is finite and exact.

The checker rejects:

- A constructor named twice.
- A constructor outside the family.
- A constructor excluded by the scrutinee’s refinement.
- Anything after the default.
- A default with no remaining constructors.

There are initially no:

- Guarded patterns
- Or-patterns
- Nested structural patterns
- Numeric or string patterns
- Fallthrough
- Pattern ordering precedence

This avoids turning elimination into a separate pattern language.

## 9. Nested elimination

Nested data is handled by nesting ordinary case expressions.

Conceptually, a `Tree (Option T)` consumer may:

1. Eliminate the tree.
2. In the `Leaf` branch, eliminate the contained option.
3. In the `Branch` branch, recurse into the two trees.

Each case form independently checks:

- Its scrutinee family.
- Its possible constructor set.
- Its payload bindings.
- Its coverage.
- Its result type.

No nested-pattern syntax is required to express nested algebraic data. If repetition later demonstrates a real need, destructuring patterns can be reconsidered with application evidence.

## 10. Branch-result typing

A case expression has one result type.

### With an expected result type

When context provides an expected type `R`, every branch is checked against `R`.

This is especially important for:

- Protocol-valued results
- Payload-free generic constructors
- Generic method results
- Function-valued branches

For example, an `Option.map` method expecting `Option U` allows:

- The `None` branch to construct `None` using expected `Option U`.
- The `Some` branch to construct `Some` from a value of type `U`.

### Without an expected result type

The checker creates a fresh result variable and collects constraints from every reachable branch.

Branches must unify under Aloe’s normal type rules. Branch order must not affect the result.

For the same nominal family:

- Family identity and generic arguments must unify.
- Constructor refinements join by taking the union of possible constructors.

Thus:

```text
None branch : Option Int refined to None
Some branch : Option Int refined to Some
result      : Option Int with {None, Some}
```

If every branch returns `Some`, the result may retain the `Some` refinement.

### Protocol results

Aloe should not automatically search for a shared protocol when branches produce unrelated nominal families.

If one branch returns `Sym` and another returns `Prod`, both of which conform to `Math`, the case needs an expected `Math` from a method return, parameter, or later type-ascription facility.

This preserves the current bidirectional model and avoids introducing least-upper-bound search across open protocol relationships.

### Generic results

Method-local result parameters work through ordinary expected-type propagation.

Conceptually:

```text
fold : ... → R
map  : ... → Option U
```

Every branch checks against the same fresh instantiation of `R` or `U`. No special “case polymorphism” or higher-rank branch type is introduced.

## 11. Refinement inside branches

An explicit branch provides authoritative constructor knowledge.

Within a `Some` branch:

- The whole binder exposes family messages.
- It also exposes `Some` payload and local messages.
- Its payload has the declaration-substituted type.
- Passing the whole value where plain `Option T` is required may forget the refinement.
- Converting it to an implemented protocol forgets constructor knowledge.

Within a default branch, the possible set is the constructors not already named. If that residual set has multiple cases, no case-local selector is available.

Arbitrary predicates remain non-refining:

```text
(option some?)  ; returns Bool, but does not authorize payload access
```

This preserves the distinction between ordinary behavior and proof-producing elimination.

## 12. Constructor additions

For a case expression without a default, adding a constructor produces a missing-branch diagnostic when the consumer is rechecked.

For example, extending:

```text
EntryKind = RegularFile | Directory | SymbolicLink | Other
```

with another constructor causes every explicitly exhaustive consumer of the full family to report the new omission.

It does not affect:

- A case whose scrutinee was already refined to an older singleton constructor.
- A case with a final default.
- Code using only family messages.
- Case-local code belonging to another constructor.

This complements Decision 3:

- Case-complete family methods report missing implementation bodies.
- External exhaustive cases report missing branches.
- Uniform family methods report omissions only if their internal case expression is exhaustive without a default.

## 13. Comparison of eliminator designs

### Ordinary receiver-oriented `case` message

Conceptually:

```alo
(option case
  (fn () none-result)
  (fn (value) some-result))
```

Advantages:

- Uses ordinary send syntax.
- Keeps the receiver first.
- Can encode lazy branches with function objects.

Costs:

- Constructor association is positional rather than named.
- Every family needs a generated heterogeneous handler signature.
- Branches require explicit function ceremony and `call` semantics.
- Refined whole-value bindings become difficult to express.
- Adding a constructor appears as an arity mismatch rather than a missing named case.
- `case` pollutes ordinary message reflection.
- Generic branch-result typing becomes part of every generated method.

Recommendation: reject as the primitive facility. A family may still define a domain-specific fold message as a library abstraction.

### Conventional dedicated case expression

Conceptually:

```text
case value of ...
```

Advantages:

- Direct static representation.
- Natural binding and exhaustiveness.
- Straightforward implementation.

Cost:

- Places the eliminator before the active value.
- Introduces a control form that reads unlike Aloe’s ordinary organization.

Recommendation: retain its semantics but use a receiver-anchored shape.

### Receiver-anchored dedicated case form

Conceptually:

```alo
(value case ...)
```

Advantages:

- Active value remains first.
- Constructor labels stay literal.
- Branches remain lazy and lexical.
- Refinement is explicit and local.
- Diagnostics can name missing constructors.
- No handler objects or generated eliminator signatures are needed.

Cost:

- The parser must recognize one reserved second-position marker.
- It looks like a send while intentionally being a special form.

Recommendation: accept this small irregularity. Its semantics are materially different from an ordinary send, and the receiver-first presentation makes that difference fit Aloe.

### Per-constructor message dispatch only

Decision 3’s case-complete methods express operations owned by the family beautifully. They do not solve exhaustive processing by downstream consumers without editing the family.

Recommendation: keep as the complementary internal mechanism, not the universal eliminator.

### Visitor or handler protocol

A visitor could require one method per constructor, and the family could send itself to the visitor.

This offers extensible operation objects but introduces:

- A new class or protocol per elimination.
- Generic result-type plumbing.
- Additional dispatch steps.
- Boilerplate for local and nested cases.
- A competing object encoding for closed representation knowledge.

Recommendation: reject as the language primitive. Libraries remain free to build visitors when persistent operation objects are genuinely useful.

### Full structural pattern matching

Nested patterns, guards, alternatives, literals, and destructuring are more expressive, but they introduce a second substantial language for coverage and binding.

Recommendation: begin with flat constructor elimination and ordinary nesting.

## Decision 4 recommendation

Approve the following elimination model:

- One receiver-anchored exhaustive case special form.
- The scrutinee is evaluated exactly once.
- Case selection uses constructor identity.
- Constructor labels are literal and family-relative.
- Explicit branches bind the refined whole value and precisely typed payloads.
- Coverage is checked against the scrutinee’s current possible-constructor set.
- Missing, duplicate, unknown, and unreachable branches receive distinct diagnostics.
- Every case is exhaustive, either explicitly or through one final default.
- A default intentionally covers future constructors and suppresses missing-case diagnostics.
- Branches share one bidirectionally checked result type.
- Same-family branch refinements join by constructor-set union.
- Unrelated nominal results require an expected common protocol rather than automatic protocol search.
- Nested cases use ordinary nesting; no initial pattern language.
- Open protocols cannot be exhaustively eliminated.
- Case-complete messages remain the receiver-owned complement to external elimination.
