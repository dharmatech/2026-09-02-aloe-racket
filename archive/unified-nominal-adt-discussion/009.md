## Decision 9: Concrete syntax

My recommendation is to make `define-family` the single nominal data declaration. Products and variants differ only in the number of explicitly declared constructors.

Construction remains an ordinary send:

```aloe
(Point new 1 2)
(Option Some 1)
(Option None (type Int))
```

The only new expression form is the receiver-anchored exhaustive `case`.

### 1. Family declaration grammar

The declaration shape is:

```text
FamilyDeclaration ::=
  (define-family FamilyHeader
    ConformanceSection?
    ConstructorSection
    FactorySection?
    FamilyMethodSection?)

FamilyHeader ::=
    Name
  | (Name TypeVariable ...)

ConformanceSection ::=
  (conforms ProtocolName ...)

ConstructorSection ::=
  (constructors Constructor ...)

Constructor ::=
  (ConstructorSelector
    (fields Field ...)
    LocalMethodSection?)

Field ::=
  (name Type)

FactorySection ::=
  (factories Method ...)

FamilyMethodSection ::=
  (methods FamilyMethod ...)

LocalMethodSection ::=
  (methods Method ...)
```

Sections have that fixed order:

1. optional `conforms`;
2. required `constructors`;
3. optional `factories`;
4. optional whole-family `methods`.

Every family has at least one constructor. Empty optional sections are normally omitted. Each constructor always has an explicit `fields` section, including zero-payload constructors.

This makes the representation visually unmistakable without requiring a second `class` construct.

### 2. A one-constructor product

The current generic `Point` becomes:

```aloe
(define-family (Point T)
  (constructors
    (new
      (fields
        (x T)
        (y T))))
  (methods
    (+ (other (Point T)) (Point T)
      (Point new
        ((self x) + (other x))
        ((self y) + (other y))))

    (dot (other (Point T)) T
      (((self x) * (other x)) +
       ((self y) * (other y))))))
```

Construction remains:

```aloe
(Point new 10 20)
```

There is no automatically generated `new`. It is an explicitly declared representation constructor named `new`.

The additional declaration ceremony is small:

```aloe
(constructors
  (new
    (fields ...)))
```

and, importantly, the same form works for every nominal family.

### 3. A multi-constructor family

`Option` is:

```aloe
(define-family (Option T)
  (constructors
    (None
      (fields))
    (Some
      (fields
        (value T))))
  (methods
    (present? () Bool
      (per-constructor
        (None #f)
        (Some #t)))))
```

Its ordinary construction sends are:

```aloe
(Option Some 10)
(Option None (type Int))
```

Constructor selectors are ordinary selector symbols. Capitalization is conventional rather than enforced, so `None`, `Some`, and `Branch` coexist naturally with a product constructor named `new`.

Constructors are not environment bindings:

```aloe
Some
```

does not evaluate to a constructor value. A first-class constructor-like function remains explicit:

```aloe
(fn (value) (Option Some value))
```

### 4. Constructor declarations

A constructor declaration contains:

- its selector;
- one required `fields` section;
- an optional local `methods` section.

It has no body and no explicit result type. Its result is necessarily its owning family instantiated with the family parameters.

For example:

```aloe
(define-family (Tree T)
  (constructors
    (Leaf
      (fields
        (value T)))
    (Branch
      (fields
        (left (Tree T))
        (right (Tree T))))))
```

Construction is:

```aloe
(Tree Leaf 10)
(Tree Branch left-tree right-tree)
```

Constructor-specific type parameters, existential fields, GADT result equations, and explicit constructor result annotations are not part of this design. Payload declarations use the family parameters under the regular-recursion rules from Decision 5.

Constructor selectors are unique and cannot be overloaded. A constructor selector is reserved throughout its owning family from factories, family messages, local messages, and additive extensions.

The type object and instance surfaces are operationally different, but reserving the constructor spelling family-wide keeps every constructor label unambiguous in sends, reflection, and case clauses.

### 5. Payload fields and local methods

Each payload field generates a zero-argument local accessor, as current class fields do.

A constructor may also declare local methods:

```aloe
(define-family Entry
  (constructors
    (Directory
      (fields
        (path String))
      (methods
        (child-path (name String) String
          (((self path) append "/") append name))))

    (Regular
      (fields
        (path String)
        (size Int))
      (methods
        (empty? () Bool
          ((self size) = 0))))

    (Other
      (fields
        (path String)))))
```

Inside a local method, `self` is singleton-refined to the owning constructor.

Payload and local selectors:

- must be unique within that constructor except for valid local overloads;
- may repeat on other constructors;
- do not become whole-family messages through repetition;
- cannot collide with a whole-family selector.

There is no visibility syntax initially because all representation constructors are public.

### 6. Factories

Factories are declared on the family type object:

```aloe
(define-family (Option T)
  (constructors
    (None
      (fields))
    (Some
      (fields
        (value T))))
  (factories
    (when (condition Bool) (value T) (Option T)
      (if condition
          (self Some value)
          (self None)))))
```

Within a factory body, `self` is the family’s type object. It can send constructor or other factory messages normally:

```aloe
(self Some value)
(self None)
```

Factories use the existing method grammar, have explicit return types, and may overload one another. Their selectors cannot collide with representation constructors.

A factory call is an ordinary send:

```aloe
(Option when ready? value)
```

No surface punctuation distinguishes it from construction. Reflection’s signature role reports whether the selected type-object row is a constructor or factory.

### 7. Method syntax remains familiar

The existing method-row syntax remains:

```text
(selector (parameter Type) ... ReturnType body)

(selector () ReturnType body)

(selector
  (type U ...)
  (parameter Type) ...
  ReturnType
  body)
```

For example:

```aloe
(map
  (type U)
  (f (-> T U))
  (Option U)
  body)
```

Protocol signatures retain the same shape without a body:

```aloe
(define-protocol Show
  (show () String))
```

Protocols themselves remain non-generic initially.

### 8. Whole-family implementation modes

A whole-family method has either an ordinary uniform body or a declaration-only `per-constructor` body table.

#### Uniform body

```aloe
(methods
  (keep (fallback T) T
    fallback))
```

Here, `self` is unrefined unless the family has only one constructor.

A uniform body may explicitly eliminate `self` with the ordinary case expression if desired.

#### Per-constructor body table

```aloe
(methods
  (present? () Bool
    (per-constructor
      (None #f)
      (Some #t)))

  (show () String
    (per-constructor
      (None "none")
      (Some ((self value) text)))))
```

`per-constructor` is recognized only as the body mode of a whole-family method declaration. It is not a general expression.

Each branch contains:

```text
(ConstructorSelector body)
```

There are no binders because:

- ordinary method parameters are already in scope;
- `self` is singleton-refined in each body;
- payload values are available through that constructor’s local field accessors.

The table must contain every constructor exactly once. It has no `else` clause. Branch order is semantically irrelevant, although declaration order is the canonical style.

Local methods and factories always have ordinary bodies. They cannot use this declaration mode.

### 9. Exhaustive case syntax

The expression grammar is:

```text
CaseExpression ::=
  (scrutinee case CaseClause ... DefaultClause?)

CaseClause ::=
    (ConstructorSelector (payload-name ...) body)
  | (ConstructorSelector whole-name (payload-name ...) body)

DefaultClause ::=
    (else body)
  | (else whole-name body)
```

The entire form must contain at least one explicit or default clause.

A basic `Option` elimination is:

```aloe
(option case
  (None () fallback)
  (Some (value) value))
```

A clause with the optional refined whole-value binder is:

```aloe
(option case
  (None () fallback)
  (Some some (value)
    (some or fallback)))
```

Within the `Some` branch:

```text
some  : Option T, refined to Some
value : T
```

A zero-payload constructor still has an explicit empty binder list:

```aloe
(None () body)
```

If its whole value is needed:

```aloe
(None none () body)
```

This consistent position makes payload arity visible even for nullary constructors.

### 10. Default clause syntax

A final default uses `else`, matching `cond`:

```aloe
(value case
  (Known (payload) known-body)
  (else other fallback-body))
```

Without a whole-value binding:

```aloe
(value case
  (Known (payload) known-body)
  (else fallback-body))
```

The default clause:

- must be final;
- is legal only when it covers at least one possible constructor;
- has no payload binders;
- may bind the entire residual-refined value;
- explicitly opts out of future missing-constructor diagnostics.

A representation constructor named `Other` remains an ordinary explicit clause:

```aloe
(entry case
  (Directory (path) ...)
  (Regular (path size) ...)
  (Other (path) ...))
```

It is unrelated to `else`.

### 11. Case syntax properties

Constructor labels in case clauses are unqualified because the scrutinee’s nominal family supplies their namespace:

```aloe
(option case
  (Some (value) ...)
  (None () ...))
```

There is no `Option.Some` expression or global `Some` binding.

Clauses may be written in any order; declaration order is preferred. Missing-case diagnostics still report constructors in declaration order.

Each branch has exactly one expression. Nested elimination uses another receiver-anchored case:

```aloe
(outer case
  (Some (inner)
    (inner case
      (None () ...)
      (Some (value) ...)))
  (None () ...))
```

There are no guards, nested patterns, alternatives, fallthrough clauses, or wildcard payload patterns initially. An unwanted payload still receives an ordinary lexical name.

### 12. Reserved case markers

`case` becomes a reserved second-position marker:

```aloe
(receiver case ...)
```

Such a list is always parsed as the exhaustive case form, never as an ordinary send. No message or constructor may therefore use `case` as its selector.

`else` is reserved only as the head of a case or `cond` clause and cannot be a representation-constructor selector.

`per-constructor` is reserved only in the body-mode position of a whole-family declaration.

Other section words such as `constructors`, `fields`, `factories`, `conforms`, and `methods` are special only in their declaration positions. They need not become globally reserved message selectors.

### 13. Explicit static type arguments

A send may contain one optional type-argument header immediately after its selector:

```text
(receiver selector (type Type ...) argument ...)
```

The header is static syntax. Its contents are type expressions and are not evaluated as argument expressions.

Examples:

```aloe
(Option None (type Int))
(Option Some (type Math) x)
(Result Error (type Int String) "failed")
(Point new (type Float) 0.0 1.0)
```

Omitting the header requests inference:

```aloe
(Option Some 10)
(Point new 0.0 1.0)
```

This preserves the fundamental send shape:

- the first item is still the receiver;
- the second item is still the literal selector;
- runtime arguments still follow it.

The `type` list is merely an optional static header within the send.

#### Ordering

For a send to a family type object, explicit arguments correspond in order to:

1. the family declaration’s parameters;
2. any row-local factory type parameters.

For an instance send, family parameters are already fixed by the receiver, so the header supplies only row-local method parameters.

All applicable type parameters must be supplied when the header is present. There is no partial `_` syntax initially. Either provide the complete list or omit the header and use inference.

The header works consistently for constructors, factories, and polymorphic methods. Candidate overloads whose generic arity does not match are inapplicable.

A `(type ...)` form immediately after a selector is therefore reserved as static send metadata and cannot simultaneously mean a runtime first argument.

### 14. Types and refinements in source

The existing type grammar remains:

```aloe
Point
(Point Float)
(Option Int)
(Result Int String)
(Tree Math)
(List (Option Int))
```

A constructor name never appears as a type:

```text
Some Int             not a type
(Option.Some Int)    not a type
```

Constructor-set refinements remain internal checker knowledge. There is no source annotation for:

```text
Option Int @ Some
Option Int @ {None, Some}
```

This keeps public method, field, protocol, function, and container types nominal and stable.

Expected types continue to come from:

- method and function parameter annotations;
- declared results;
- protocol positions;
- enclosing expression constraints.

The explicit send type header handles cases such as a context-free `None` without introducing a general cast or ascription expression.

### 15. Additive extension syntax

`define-methods` remains the extension form used by MPL. It gains an optional `factories` section while retaining the existing `methods` section:

```text
(define-methods FamilyName
  FactorySection?
  FamilyMethodSection?)
```

At least one section must be present, in `factories`-then-`methods` order.

Existing family extensions remain recognizable:

```aloe
(define-methods Sym
  (methods
    (+ (other Math) Math
      body)))
```

A type-object extension is:

```aloe
(define-methods Point
  (factories
    (diagonal (value T) (Point T)
      (self new value value))))
```

A single form may add both:

```aloe
(define-methods Point
  (factories
    ...)
  (methods
    ...))
```

The target family’s generic parameters are in scope, as `T` is for current `define-methods List`.

Extensions may add:

- factories;
- uniform whole-family methods;
- compatible overload rows.

They may not add:

- constructors;
- fields;
- local methods;
- `per-constructor` body tables;
- conformance claims;
- replacement rows.

An external whole-family method that needs case knowledge uses an ordinary exhaustive case expression on `self`.

### 16. Protocol conformance syntax

The current positional protocol after a class name does not scale to multiple protocols. It is replaced by the explicit optional section:

```aloe
(define-family Sym
  (conforms Math Show)
  (constructors
    (new
      (fields
        (name String))))
  (methods
    ...))
```

An absent `conforms` section means no protocols. An empty section is rejected rather than retained as noise.

Conformance remains declaration-owned. There is no external form such as:

```text
(define-conformance ExistingFamily Protocol)
```

Methods required by a declared conformance may still be supplied by additive `define-methods` forms before whole-program conformance validation.

### 17. Reflection selector spellings

Decision 8 added two descriptive facts to `Signature`. Their concrete selectors should be:

```aloe
(signature role)
(signature type-params)
```

Their result types are:

```text
role        : Symbol
type-params : (List Symbol)
```

`role` returns an interned symbol whose name is one of:

```text
constructor
factory
family
local
operation
```

The existing reflection vocabulary remains:

```aloe
(signature selector)
(signature params)
(signature return)
(signature accepts? candidate-mirror)

(mirror messages)
(mirror signatures)
(mirror invoke signature argument ...)
(mirror subject)
(mirror raw)
```

There is no `mirror constructor`, `mirror payload`, `mirror type`, or general dynamic cast syntax.

The exhaustive `case` form is syntax, so it never appears in reflected messages.

### 18. Raw rendering

The concise raw spelling should be:

```text
#<Point 1 2>
#<Option.None>
#<Option.Some 1>
#<Tree.Branch #<Tree.Leaf 1> #<Tree.Leaf 2>>
```

Rules:

- a one-constructor family prints the family label and payloads, omitting the redundant constructor label;
- a multi-constructor family prints `Family.Constructor`;
- payloads follow in declaration order;
- a zero-payload constructor ends immediately after the qualified label;
- names remain presentation labels, not identities;
- raw output is not parseable source or serialization.

Normal display may still use `show`; `:raw` and `(mirror raw)` use this structural form.

When exact generic instantiation matters, type-aware diagnostics show it separately using ordinary type grammar:

```text
value: #<Option.None>
type:  (Option Int)
```

This keeps normal `Point` and `Option` output readable while still allowing runtime type mismatches to distinguish otherwise identical parameterless values.

### 19. Complete examples

#### `Result`

```aloe
(define-family (Result T E)
  (constructors
    (Ok
      (fields
        (value T)))
    (Error
      (fields
        (error E))))
  (methods
    (successful? () Bool
      (per-constructor
        (Ok #t)
        (Error #f)))))
```

Construction:

```aloe
(Result Ok 10)
(Result Error (type Int String) "not found")
```

Elimination:

```aloe
(result case
  (Ok (value)
    value)
  (Error failed (message)
    (failed log message)))
```

#### Recursive `Tree`

```aloe
(define-family (Tree T)
  (constructors
    (Leaf
      (fields
        (value T)))
    (Branch
      (fields
        (left (Tree T))
        (right (Tree T)))))
  (methods
    (size () Int
      (per-constructor
        (Leaf 1)
        (Branch
          (((self left) size) + ((self right) size)))))))
```

External elimination:

```aloe
(tree case
  (Leaf (value)
    value)
  (Branch node (left right)
    ((left size) + (right size))))
```

### 20. Source-language transition

The unified language should remove `define-class` rather than retain it as a permanent alias.

A current class moves mechanically:

```aloe
(define-class (Point T)
  (fields
    (x T)
    (y T))
  (methods
    ...))
```

becomes:

```aloe
(define-family (Point T)
  (constructors
    (new
      (fields
        (x T)
        (y T))))
  (methods
    ...))
```

Existing construction remains `(Point new ...)` because `new` is now the explicitly declared sole constructor.

The existing positional protocol name moves into `(conforms ...)`. Existing `define-methods` extensions largely retain their shape.

I would not keep both `define-class` and `define-family` in the normative language. That would preserve two apparent ontologies after we had deliberately chosen one. A temporary migration tool or implementation compatibility window can be considered in Decision 10, but it is not language semantics.

### 21. Alternatives I would reject

I would reject:

- **Separate `define-class` and `define-variant`:** preserves the ontology split.
- **Constructor application such as `(Some value)`:** violates receiver-first send semantics.
- **Globally bound constructor functions:** introduces a second construction mechanism and name collisions.
- **Implicitly generated `new`:** hides the representation constructor in the one-constructor case.
- **Top-level `match value` syntax:** loses the receiver-first shape.
- **Qualified case labels such as `Option.Some`:** redundant because the scrutinee already anchors the family.
- **Handler-function or visitor syntax as the primary eliminator:** adds more ceremony and weaker diagnostics.
- **A full nested-pattern grammar immediately:** unnecessary for the first applications.
- **Constructor-specific result annotations:** opens the door to GADTs before Aloe has the required type theory.
- **A permanent `define-class` compatibility alias:** leaves two mental models in the language.
- **A positional conformance list after the family header:** becomes visually ambiguous as protocols multiply.
- **A general cast or type-ascription special form solely for `None`:** the optional send type header solves the actual problem more locally.
- **A separate extension construct for factories:** extending `define-methods` with a labeled `factories` section is smaller.
- **Exposing constructors as reflective instance tags:** contradicts Decision 8.

### Syntax nucleus

The compact surface is:

```aloe
(define-family (Option T)
  (constructors
    (None
      (fields))
    (Some
      (fields
        (value T))))
  (methods
    (present? () Bool
      (per-constructor
        (None #f)
        (Some #t)))))

(define maybe
  (Option None (type Int)))

(maybe case
  (None () 0)
  (Some (value) value))
```

This remains recognizably Aloe:

- definitions are explicit s-expressions;
- construction is a send;
- selectors remain literal;
- type syntax remains confined to explicit annotation positions;
- methods remain receiver-owned;
- exhaustive elimination remains receiver-anchored;
- one constructor and many constructors use exactly one nominal declaration model.

I recommend adopting this as Decision 9. I’ll stop here for review before recording it or moving to Decision 10.
