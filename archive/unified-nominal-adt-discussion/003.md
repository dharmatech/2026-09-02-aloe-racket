# Decision 3: Which messages does an algebraic value understand?

The recommended model separates a message’s public availability from the way its body is implemented:

> A family message is an explicit promise available on every constructor. A case-local message is available only with singleton constructor knowledge. Each family message has either one uniform body or an exhaustive table of per-constructor bodies—but never a default body plus overrides.

This preserves receiver-oriented programming without introducing inheritance, virtual overrides, or an implicit visitor system.

## 1. Two instance-message surfaces

Every nominal declaration owns two levels of instance behavior.

### Whole-family messages

A family message is explicitly declared as valid for every value of the nominal family.

Given only `Option Int`, tooling may offer messages such as:

```text
empty?  : Bool
map     : ...
or      : Int → Int
```

The receiver does not need to be refined. Protocol-required operations must be represented by family messages because protocol conformance is a promise made by the whole family.

### Case-local messages

A case may additionally own messages that make sense only for that representation.

For example:

```text
Some
  value : T

RegularFile
  facts    : FileFacts
  contents : ...

SymbolicLink
  facts  : LinkFacts
  target : ...
```

Payload accessors are zero-argument case-local messages. Additional case-specific methods use the same surface.

An unrefined `Option Int` cannot receive `value`, because it might be `None`. A value refined to `Some` can receive it normally.

Case-local messages do not create distinct case types. They are rows guarded by constructor identity.

## 2. Selector discovery

The statically discoverable surface follows the receiver knowledge:

| Receiver knowledge | Available selectors |
|---|---|
| Type object | Representation constructors and ordinary type-object messages |
| Unrefined family value | Whole-family messages |
| Value refined to constructor `C` | Whole-family messages plus `C`’s payload and local messages |
| Protocol value | Protocol-declared messages |
| One-constructor family value | Family messages plus its sole constructor’s local surface |

The last rule preserves product ergonomics. Every `Point T` is necessarily its sole constructor, so `x`, `y`, and its other messages remain immediately available.

Refinement adds selectors monotonically: learning the constructor never removes a family selector.

## 3. Family messages are explicit

Aloe should not infer a family message merely because every current constructor happens to define the same selector.

For example, if three cases independently define a local `name` message, `name` does not silently become a family message. The declaration must explicitly promise it family-wide.

This provides several benefits:

- Adding a constructor cannot silently remove a selector from the family surface.
- Signatures need not be compared structurally to infer an accidental intersection.
- Differently typed local uses of the same selector remain legal.
- Protocol conformance has an explicit surface to check.
- Diagnostics can distinguish “missing family implementation” from “case-local message unavailable.”

The same case-local selector may appear on several constructors. It remains unavailable without singleton refinement unless promoted through an explicit family declaration.

## 4. Two implementation forms for a family message

A family message signature may be implemented in one of two ways.

### Uniform body

A uniform family body is checked with `self` known only as the family.

It may:

- Call other family messages.
- Use its parameters.
- Construct values.
- Exhaustively eliminate `self` when it needs representation-specific data.

It may not directly access a particular case payload or call a case-local message without refinement.

For a one-constructor family, `self` is inherently refined to the sole constructor, so the body may access fields exactly as today.

### Case-complete bodies

A family message may instead provide exactly one implementation body for every representation constructor.

Each body:

- Has the same family-visible signature.
- Receives the same runtime value as `self`.
- Checks `self` under that constructor’s singleton refinement.
- May access that case’s payload and local messages directly.

The declaration must supply every constructor exactly once. Missing or duplicate bodies are declaration errors.

This is ordinary receiver-oriented behavior: sending the family message dynamically selects the body belonging to the receiver’s constructor.

### No defaults and overrides

A given family message row may not combine a uniform default body with selected case overrides.

That model would introduce:

- Override precedence.
- Questions about inherited versus replaced behavior.
- Partial coverage that looks exhaustive but is not.
- A second notion of method specificity based on receiver cases.

Aloe has no inheritance, and algebraic constructors do not need to recreate it.

Each overload independently chooses one implementation form: one uniform body or one exhaustive constructor-indexed body table.

## 5. Why both implementation forms earn their place

Requiring only uniform bodies would force internal elimination for nearly every useful operation on `Option`, `Result`, or `Tree`.

Requiring only per-constructor bodies would duplicate representation-independent algorithms and make operations that naturally consume the whole family unnecessarily repetitive.

The two forms represent genuinely different designs:

| Uniform body | Case-complete bodies |
|---|---|
| One algorithm over the abstraction | Behavior naturally follows representation |
| `self` begins unrefined | `self` begins refined |
| Explicit elimination when needed | Constructor dispatch supplies refinement |
| Good for composed operations | Good for `map`, `fold`, `show`, state transitions |
| Adding a constructor does not inherently require a new body | Adding a constructor reports every missing body |

They remain simpler than defaults plus overrides because a message row has exactly one implementation strategy.

## 6. Case-local selectors occupy a separate namespace partition

Within one family, a selector is classified either as family-wide or case-local—not both.

Therefore:

- A case-local selector cannot add an overload beneath an existing family selector.
- A family selector cannot collide with a payload selector.
- Payload selectors are reserved within their case.
- Family overloads are declared together at the family level.
- Case-local overloads are declared within their constructor’s local surface.

This prevents a refined case from silently changing the meaning of a send already valid on the whole family.

Suppose the family offered `choose(Math)`. If one case could privately add `choose(Sym)`, a send checked against `choose(Math)` might dynamically select the hidden case overload and return a type the caller did not expect. Separating selector partitions removes that ambiguity.

If an exact `Sym` overload is useful for the family, it should be declared as a family overload. A case-complete implementation may still give every constructor its own body.

## 7. Static overload resolution

For an unrefined family receiver, overload resolution considers only the family’s rows for the selected family selector.

For a receiver refined to `C`:

- A family selector considers the same family overload rows.
- A local selector considers only `C`’s local overload rows.
- Family and local rows never compete.

Within the selected table, Aloe retains its existing rules:

1. Selector must match.
2. Arity must match.
3. Argument types must be applicable.
4. Exact nominal matches beat protocol matches.
5. Protocol matches beat unconstrained generic matches.
6. An unresolved tie is ambiguous.

Refinement affects which table is visible, not overload specificity.

## 8. Dynamic overloads require return coherence

Current MPL behavior intentionally allows runtime argument types to select an exact overload even when a send was statically checked through a broader protocol signature. For example, a send checked as returning `Math` may dynamically select a `Sym` overload returning `Prod`, which is safe because `Prod` conforms to `Math`.

That behavior should remain, but its safety requirement should become explicit:

> When one overload can dynamically replace a less-specific applicable overload, its result type must be usable wherever the less-specific result type was promised.

Conceptually:

```text
choose(Math) → Math
choose(Sym)  → Prod     ; valid when Prod conforms to Math
```

But this is invalid:

```text
choose(Math) → Math
choose(Sym)  → String
```

A call statically checked through the first row could otherwise produce a `String` at runtime.

This covariance check applies to overlapping overloads after generic substitution. Disjoint overloads such as `pick(Int)` and `pick(String)` impose no relationship.

Decision 6 will integrate this rule with complete protocol-conformance checking, but Decision 3 establishes the necessary dispatch invariant.

## 9. One runtime dispatch rule

For a runtime value with family identity `F` and constructor identity `C`, sending selector `s` proceeds conceptually as follows:

1. If `s` is a family selector, select among `F`’s overload rows.
2. Otherwise, if `s` is local to `C`, select among `C`’s local overload rows.
3. Otherwise, report an unknown message.
4. Resolve the overload using runtime argument types.
5. Execute:
   - The row’s uniform body, or
   - Its body indexed by `C`, or
   - The selected case-local body.
6. Bind `self` to the original receiver and parameters to the evaluated arguments.

Constructor identity is simply another component of the receiver’s dispatch identity. There is no visitor call, case-object delegation, inherited lookup, or generic-function dispatch.

A checked program cannot send a local selector to an unrefined family value. Runtime local lookup remains necessary for refined sends, exact reflected invocation, and defensive checking.

## 10. Sources of refinement

The initial language should recognize constructor refinement only from semantically authoritative sources:

- A direct representation-constructor result.
- The corresponding arm of exhaustive elimination.
- `self` inside a per-constructor family body.
- `self` inside a case-local body.
- A local alias whose value knowledge has not been widened.

The checker should not refine from:

- An arbitrary Boolean predicate such as `some?`.
- Constructor-name strings or symbols.
- Structural equality.
- `Mirror` observations.
- User methods that merely claim something about the receiver.
- Runtime failure of a message.

This avoids a general theorem-proving or occurrence-typing system. A predicate may still be useful for ordinary control flow, but payload access requires authoritative elimination.

A boundary requiring the plain family type or a protocol may forget singleton knowledge. Decision 5 will specify precisely how refinements join and propagate through functions, generics, collections, and branch results.

## 11. Representative behavior

### `Point T`

`Point` has one representation constructor.

- `x` and `y` are constructor payload messages.
- They are always available because every `Point` has that constructor.
- Arithmetic such as `+` is a family message.
- A uniform `+` body may read `x` and `y` because `self` is inherently singleton-refined.

The common product case remains equivalent to today’s class experience.

### `Option T`

`Option T` has `None` and `Some`.

Possible family messages include:

```text
empty? : Bool
map    : ...
or     : T → T
```

`Some` additionally exposes its payload selector. `None` does not.

`map` is naturally a family message with case-complete bodies:

- The `None` body constructs `None`.
- The `Some` body accesses the payload and constructs `Some`.

External code may instead eliminate an `Option` exhaustively when its desired operation should not belong to the type.

### `Tree T`

`fold`, traversal, or size are family messages. Case-complete bodies let:

- `Leaf` access its element.
- `Branch` access its two recursive children.

A uniform body remains available when the algorithm is clearer as explicit elimination.

### Filesystem entries

Every `EntryKind` may provide family messages such as `facts-summary` or `display-name`.

After refinement:

- `RegularFile` may expose regular-file operations.
- `Directory` may expose directory-specific operations.
- `SymbolicLink` may expose its target.
- `Other` exposes only its declared payload and local behavior.

A `(List EntryKind)` continues to expose only the family surface when elements are retrieved.

### MPL

`Math` remains an open protocol. Existing one-constructor families such as `Sym`, `Prod`, and `Pow` expose their operations as family messages.

Their exact overloads remain dynamically useful, subject to compatible-result checking. A future multi-constructor algebraic family may conform to `Math`, but every required `Math` selector must be family-wide. Its implementation may use either a uniform body or complete case bodies.

## 12. Adding a constructor

Adding a new representation constructor causes targeted consequences:

- Every case-complete family message reports its missing body.
- Uniform family bodies remain valid unless their internal elimination becomes non-exhaustive.
- Existing exhaustive consumers report the missing constructor.
- Protocol conformance is rechecked through the family surface.
- Existing case-local messages remain local and unchanged.
- The family selector set does not change accidentally.

This is the desired closed-data maintenance story: additions produce explicit, bounded diagnostics rather than silently changing dispatch.

## Alternatives considered

### Only uniform family bodies

This has the smallest declaration machinery but forces routine closed-data behavior through repeated elimination. It underuses Aloe’s receiver model.

### Only per-constructor bodies

This makes dispatch straightforward but duplicates uniform algorithms and forces every operation to mention every constructor.

### Default family body plus case overrides

This resembles inheritance and virtual overriding. It introduces precedence and partial-coverage semantics that Aloe otherwise avoids.

### Implicit intersection surfaces

A selector implemented by every case could automatically become family-wide. This makes the API sensitive to coincidental case structure and causes adding a constructor to remove previously available messages.

### Case-local overloads beneath family selectors

This is expressive but permits hidden runtime interception of sends checked against the family surface. Keeping selector partitions disjoint is smaller and more predictable.

## Decision 3 recommendation

Approve the following message model:

- Whole-family messages are explicit guarantees.
- Cases may define additional payload and behavior messages.
- Singleton refinement adds that case’s local selectors.
- The same selector cannot be both family-wide and case-local.
- A family message row has either one uniform body or exactly one body per constructor.
- Defaults plus overrides are not supported.
- One-constructor families retain direct field and method ergonomics.
- Family and case-local overload tables never compete.
- Existing runtime most-specific overload behavior remains, with compatible-result checking for overlapping rows.
- Direct construction, elimination arms, and constructor-specific bodies are the authoritative sources of refinement.
- Runtime dispatch remains one receiver-first algorithm using family identity, constructor identity, selector, and argument types.
