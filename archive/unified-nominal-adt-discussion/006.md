# Decision 6: How do open protocols and closed algebraic data coexist?

The recommended model is:

> Every user-declared nominal family may explicitly conform to any number of open protocols. Conformance belongs to the whole family, never to an individual constructor. Protocols remain nominal message contracts—not method tables—and runtime sends continue through the concrete family and constructor.

This gives Aloe two complementary forms of abstraction:

- Closed constructor knowledge for exhaustive data processing.
- Open protocol conformance for downstream behavioral extension.

Neither is encoded in terms of the other.

## 1. Every nominal family may implement protocols

A family’s number of representation constructors does not affect its eligibility.

All of these may conform:

```text
Sym
Point T
Option T
EntryKind
Tree T
GelMode
```

A one-constructor product and a many-constructor family use the same conformance rule.

A multi-constructor family satisfies a protocol through family messages. Those messages may use either implementation form from Decision 3:

- One uniform body checked against the unrefined family.
- A complete constructor-indexed body table.

Thus a closed family can provide genuinely constructor-dependent protocol behavior without turning each constructor into a separate protocol implementation.

## 2. Conformance is explicit and nominal

Merely possessing appropriately named messages does not make a family conform.

A declaration must explicitly identify each protocol it implements. The protocol and family are both resolved by nominal declaration identity, not their spelling or structural shape.

This prevents accidental conformance when:

- A family happens to use the same selector.
- An unrelated protocol is added later.
- Two modules eventually contain same-named declarations.
- A message extension happens to complete a structural signature.

Explicit conformance is also what authorizes family-to-protocol conversion.

## 3. Multiple protocols replace the one-protocol restriction

The current one-protocol-per-class restriction should disappear.

A family may explicitly conform to zero or more protocols:

```text
Family F conforms to P, Q, R
```

This does not introduce protocol inheritance or intersection types.

A value of `F` may be used wherever any one of `P`, `Q`, or `R` is expected. A variable viewed as `P` exposes only `P`’s surface; it does not implicitly carry a source-visible `P & Q` type.

Duplicate conformance declarations are errors.

Multiple protocols pay for themselves immediately:

- Mathematical values need not choose between `Math`, presentation, and future serialization contracts.
- Filesystem values may have independent naming and presentation behavior.
- Gel states may participate in presentation without making presentation part of their representation.
- One artificial “everything this type does” protocol is unnecessary.

## 4. Protocol conformance requires family messages

A protocol requirement cannot be satisfied by:

- A constructor message on the type object.
- A factory.
- A case-local message.
- A payload accessor available only after refinement.
- A reflective operation.
- A message that merely exists on some constructors.

It must be satisfied by an explicit whole-family message row.

This ensures a protocol-typed caller can safely send the required selector regardless of the receiver’s constructor.

For a one-constructor family, ordinary product methods naturally become family messages. Payload accessors do not automatically become protocol implementations unless the family explicitly exposes an appropriate family operation.

## 5. Signature compatibility

For each protocol signature, the family must provide a compatible family overload.

Compatibility follows ordinary behavioral substitutability.

### Parameters

The family implementation must accept every argument the protocol permits.

Therefore:

```text
protocol requires: compare(Math)
family provides:   compare(Sym)
```

is invalid because the implementation is narrower.

The opposite may be valid:

```text
protocol requires: compare(Sym)
family provides:   compare(Math)
```

because every `Sym` is usable as `Math`.

With Aloe’s initial type relations, parameter compatibility uses:

- Exact nominal equality.
- Family-to-protocol conformance.
- Invariant generic arguments.
- Ordinary function-type compatibility when relevant.

### Results

The family result may be more specific than the protocol result.

For example:

```text
protocol requires: combine(Math) → Math
family provides:   combine(Math) → Prod
```

is valid when `Prod` conforms to `Math`.

A family result cannot be unrelated to the promised protocol result.

### Overloads

A family may provide additional overloads beyond the protocol requirement.

One family row is designated as accepting the protocol’s complete argument domain. More-specific runtime overloads may still win for concrete arguments, but Decision 3’s return-coherence rule applies: every dynamically intercepting overload must return a value usable as the broader protocol result.

This preserves MPL’s intentional behavior:

- A send may be statically checked through `Math`.
- Runtime lookup may select an exact `Sym`, `Pow`, or `Prod` overload.
- The resulting concrete value must still satisfy the statically promised `Math`.

## 6. Several protocols may share messages

If two protocols require the same selector and compatible signature, one family message may satisfy both.

For example:

```text
Protocol A: name() → String
Protocol B: name() → String
```

One family `name` row is sufficient.

If their argument signatures differ, the family may provide ordinary overloads.

If they require the same selector and parameter types but incompatible result types, joint conformance is rejected. Aloe does not overload solely by return type.

For example:

```text
Protocol A: value() → String
Protocol B: value() → Symbol
```

cannot both be satisfied by one family because callers provide no result-type information to runtime selector lookup.

## 7. Generic-family conformance is uniform

Because protocols are not yet parameterized and Aloe has no generic constraints, conformance by a generic family must hold for every valid instantiation.

For example, `Option T` cannot conditionally conform to `Show` only when `T` conforms to `Show`. That would require a constraint resembling:

```text
Option T conforms to Show when T conforms to Show
```

Conditional conformance introduces:

- Protocol constraints on type parameters.
- Evidence propagation.
- Conditional overload applicability.
- More involved reflection and runtime checks.

It should wait for an application that genuinely needs it.

A generic family may conform unconditionally when its implementation does not require unsupported behavior from its parameters.

## 8. Cases do not independently implement protocols

Individual representation constructors should not initially declare conformance.

For example, Aloe should not treat:

```text
RegularFile conforms to Readable
Directory conforms to Enumerable
```

as protocol relationships when both are constructors of `EntryKind`.

That would effectively introduce hidden case subtypes:

- Protocol conversion would depend on refinement.
- Case knowledge would escape into source type relationships.
- A protocol parameter could accept only selected constructors without a source-nameable type.
- Protocol conversion would need to preserve or reconstruct case identity.
- Adding a constructor could change conditional conformance behavior.

The existing alternatives are sufficient:

- Put the behavior in a case-local message.
- Put the protocol on a precise payload type such as `FileFacts`.
- Introduce a distinct nominal wrapper or capability value when open abstraction is genuinely required.
- Make the whole family conform if every constructor can honor the contract.

Case-specific protocol conformance can be reconsidered only alongside source-nameable case views or another explicit abstraction mechanism.

## 9. Protocols can consume refined values

A refined value may be passed to a protocol whenever its whole family conforms.

Conceptually:

```text
value : F refined to C
F conforms to P
```

permits:

```text
value used as P
```

The protocol conversion forgets constructor refinement. Inside code receiving `P`:

- Only `P`’s messages are available.
- The concrete family is not statically known.
- Exhaustive case is unavailable.
- Runtime dispatch still reaches the original family and constructor.

Returning from protocol abstraction does not automatically recover the discarded refinement.

Thus protocols can abstract over refined values as ordinary family members, but cannot abstract specifically over “only constructor `C`.”

## 10. Runtime protocol sends

For a receiver statically typed as protocol `P`:

1. The checker selects a signature from `P`.
2. Arguments are checked against that signature.
3. The result receives the protocol-declared result type.
4. Runtime evaluation examines the receiver’s actual nominal family and constructor.
5. It looks up the selector in the family’s whole-family table.
6. Normal dynamic overload resolution chooses an applicable row.
7. A uniform or constructor-indexed family body executes.

The protocol contributes no runtime method body and no second dispatch table.

Constructor-local selectors cannot collide with family selectors, so a hidden case method cannot intercept a protocol send.

Reflection of the concrete value observes its concrete family rows. It does not fabricate duplicate runtime rows for every protocol the family implements.

## 11. Adding a constructor to a conforming family

When a constructor is added:

- Uniform protocol-method bodies remain family-wide.
- Case-complete protocol-method implementations report their missing constructor bodies.
- Internal exhaustive cases report the new omission unless they have defaults.
- Protocol conformance is rechecked.
- Case-local messages do not affect conformance.
- The protocol declaration itself does not change.

The family cannot remain conformant while silently leaving its new constructor without required behavior.

## 12. Protocol operations remain closed; implementations remain open

A protocol’s declared message set is closed at a given program version.

Downstream code may add new implementations by declaring new families that conform. It may not silently append requirements to an existing protocol without changing that protocol and rechecking all conformers.

This is the intended open dimension:

```text
Existing Math protocol
  + downstream Matrix family
  + downstream Polynomial family
  + downstream algebraic-number family
```

MPL does not need to know those families in advance.

Changing `Math` by adding a required operation is an intentional breaking change. Every conforming family must be updated or cease claiming conformance.

No protocol default implementations are introduced. Reusable behavior may live in ordinary functions, services, or family extensions.

## 13. Additive receiver-anchored message extensions remain useful

Aloe already has concrete evidence that method bodies sometimes need to be defined after nominal shells are known: MPL’s families refer to one another and currently use `define-methods`.

The unified model should retain the semantic capability of additive receiver-anchored extensions.

An extension may add:

- A new whole-family message with a uniform body.
- A new overload of an existing family selector.
- An ordinary type-object message or factory.

An extension may not add:

- A representation constructor.
- A payload slot.
- A case-local message.
- A constructor-specific implementation table.
- A new protocol conformance claim.
- A replacement for an existing exact method row.

This distinction protects representation while allowing separately authored operations to remain genuine, discoverable messages.

An extension body receives the family value unrefined. It may use exhaustive case internally when it needs representation-specific behavior.

### Coherence

The assembled program image must contain at most one row for an exact combination of:

```text
receiver identity
selector
parameter signature
```

Extensions may add distinct overloads, subject to ordinary ambiguity and return-coherence checks. Duplicate exact rows are errors rather than temporal replacement.

A family extension also may not claim a selector reserved by a constructor or classified as case-local.

This is additive growth, not monkey-patching replacement.

## 14. Conformance may rely on separately supplied family methods

A family’s conformance claim remains part of its declaration, but required family methods may be supplied by additive method extensions before the surrounding program is finalized.

This preserves the useful current workflow:

1. Declare protocol identities.
2. Declare mutually referring nominal family shells in a valid source order.
3. Add whole-family method bodies once referenced types are available.
4. Check final protocol conformance over the assembled surface.

The family cannot acquire a new protocol merely because an extension happens to provide matching methods. Conformance remains explicit.

Future modules will need to define ownership and visibility more precisely. The initial single-image rule is global coherence with no exact-row replacement.

## 15. Who may add what?

| Change | Initial authority |
|---|---|
| Add a constructor to an existing family | Edit the nominal declaration; downstream extension forbidden |
| Add or alter payload representation | Edit the nominal declaration |
| Add a case-local message | Edit the nominal declaration |
| Add a whole-family operation | Declaration or additive receiver-anchored extension |
| Add an ordinary type-object factory | Declaration or additive type-object extension |
| Add a new family implementing an existing protocol | Any downstream author |
| Add conformance to an existing family | Amend that family’s declaration; no retroactive orphan conformance |
| Add a required operation to a protocol | Amend the protocol and recheck every conformer |
| Add a new protocol | Any author; existing families must explicitly opt in |
| Replace an existing method row | Not permitted |

This intentionally does not claim to eliminate the expression problem.

## 16. The expression problem, stated honestly

Aloe provides different strengths along the two dimensions.

### Closed family

Because constructors are known:

- Anyone can write a new exhaustive consumer.
- New whole-family messages may be added receiver-anchored.
- Adding a constructor diagnoses affected exhaustive consumers and case-complete methods.

### Open protocol

Because implementations are unknown:

- Anyone can add a new conforming family.
- Protocol-typed code continues to dispatch to it.
- Adding a required protocol operation is a breaking change for conformers.

A new external consumer of a closed family may be:

- An exhaustive receiver-anchored case expression inside a function.
- A service object message.
- An additive family message extension.

A new operation across arbitrary existing protocol implementations cannot appear magically. It requires amending the protocol, defining another protocol with explicit opt-in, or using an external service/function that is not claimed as a receiver message.

This is the intentional tradeoff behind:

> One way to define values; two complementary ways to abstract over them.

## 17. MPL

`Math` remains an open protocol.

Existing values such as `Sym`, `Num`, `Sum`, `Prod`, and `Pow` are one-constructor nominal families conforming to `Math`. Their overloads remain family messages.

A downstream user may define a new family and explicitly conform it to `Math` without editing MPL.

A closed family may also conform. For example, a hypothetical exact-number family with integer and rational constructors could implement each `Math` message using complete per-constructor bodies.

Nothing converts `Math` into a closed `MathExpr` constructor set, and exhaustive case remains unavailable on a `Math` receiver.

## 18. Filesystem pressure

`EntryKind` may conform as a whole to protocols such as naming or presentation when every constructor supports the required behavior.

Constructor-specific capabilities remain explicit:

- `RegularFile` exposes its local operations after refinement.
- Its `FileFacts` or a returned capability object may implement an open reading protocol.
- `Directory` may expose different case-local behavior or payload abstractions.
- `Other` remains an explicit constructor.

This avoids pretending that selected cases are independently typed subclasses.

## 19. Alternatives considered

### Retain one protocol per family

This forces unrelated behavior into oversized protocols and makes ordinary combinations artificial.

Recommendation: replace it with finite multiple direct conformance.

### Structural conformance

Matching selectors could automatically satisfy a protocol. This makes conformance accidental and complicates nominal identity, diagnostics, and future evolution.

Recommendation: explicit nominal conformance.

### Per-constructor conformance

This offers attractive filesystem examples but silently reintroduces case subtypes and refinement-dependent conversions.

Recommendation: family-wide conformance only.

### Retroactive orphan conformance

Downstream code could make an existing foreign family implement a new protocol. This improves one dimension of the expression problem but introduces competing implementations, load-order dependence, and module-coherence problems.

Recommendation: no retroactive conformance initially. Use wrappers or explicit family amendments.

### Protocol default methods

Defaults would create a protocol-owned implementation table or inheritance-like fallback path.

Recommendation: protocols remain contracts. Reuse ordinary Aloe composition.

### Protocol inheritance and intersections

These may reduce repeated requirements, but introduce subtype ordering and ambiguity beyond current application needs.

Recommendation: multiple direct protocols without protocol inheritance.

### Close all family operations at declaration time

This gives strong ownership but conflicts with MPL’s existing cross-referenced organization and prevents a useful receiver-anchored extension model.

Recommendation: representation is closed; whole-family operations are additively extensible and globally coherent.

## Decision 6 recommendation

Approve the following:

- Every user-declared nominal family may explicitly conform to protocols.
- Conformance belongs to the whole family, not individual constructors.
- Refined case values may enter a family protocol, losing refinement.
- Protocol receivers cannot be exhaustively eliminated.
- Multiple direct protocols replace the current one-protocol restriction.
- Protocol inheritance, intersections, defaults, parameters, and conditional conformance remain deferred.
- Required protocol selectors must be whole-family messages.
- Parameters are checked contravariantly within Aloe’s existing type relation; results may specialize covariantly.
- More-specific runtime overloads must preserve the protocol-promised result.
- Generic-family conformance must hold uniformly for all instantiations.
- Protocols remain nominal contracts with no runtime method table.
- Downstream authors may add new conforming nominal families.
- Retroactive conformance for existing foreign families is not initially allowed.
- Receiver-anchored extensions may add coherent whole-family messages and factories, but never constructors, payloads, case-local behavior, conformance claims, or replacements.
- Protocol operation sets evolve explicitly and break conformers when requirements are added.
- The design embraces rather than obscures the expression problem’s two dimensions.
