# Decision 5: How do generics, refinements, and recursion fit together?

The recommended model is:

> Nominal family parameters remain invariant. Constructors infer one exact family instantiation from context and payload constraints. Constructor refinements are shallow static knowledge, not generic type arguments. Recursive families are regular nominal recursion: their own name may appear in payload types with the same parameters, without type unfolding or termination claims.

This supports `Option T`, `Result T E`, and `Tree T` without introducing covariance, bottom types, general let-polymorphism, or equirecursive unification.

## 1. Generic nominal families

A declaration may introduce a type constructor with a fixed arity:

```text
Option : Type → Type
Result : Type × Type → Type
Tree   : Type → Type
```

Every use supplies exactly that many type arguments, whether inferred, expected, or explicitly constrained.

The parameters are rigid while the declaration’s payloads and method bodies are checked. A family method’s own type parameters are separate and freshly instantiated at each send.

For example:

```text
Option T
  None
  Some T

Result T E
  Ok T
  Error E

Tree T
  Leaf T
  Branch (Tree T) (Tree T)
```

These are semantic descriptions, not proposed declaration syntax.

## 2. Initial invariance

All nominal generic families should initially be invariant.

Therefore:

```text
Option Sym  ≠  Option Math
List Sym    ≠  List Math
Tree Sym    ≠  Tree Math
```

even when `Sym` conforms to `Math`.

Immutability alone does not make every family covariant. Family and case messages may consume their parameters:

```text
Option T   might provide or(T)
List T     provides cons(T)
Tree T     might provide replace(T)
```

Automatically inferring variance would need to inspect:

- Constructor payload positions.
- Family and case-local method parameters.
- Function types.
- Protocol conversions.
- Future extensions.
- Overload applicability.
- Runtime reflective checks.

Invariance keeps construction, assignment, overload resolution, and runtime identity exact.

### Contextual construction is not covariance

Given an expected `Option Math`, constructing `Some` with a `Sym` payload is valid:

```text
expected: Option Math
payload:  Sym, usable as Math
result:   Option Math
```

The constructor is instantiated directly at `T = Math`. Aloe is not converting an already-created `Option Sym` into `Option Math`.

Without that expected type, the same constructor infers `Option Sym`.

Widening an existing `Option Sym` to `Option Math` requires explicit reconstruction or a family operation. There is no container-level subtype conversion.

## 3. Constructor inference revisited

Decision 2 established three sources of constructor constraints:

1. Explicit family instantiation.
2. Expected result type.
3. Payload argument types.

Decision 5 adds the completion rule:

> Constraints from the complete enclosing expression are solved together before unresolved-constructor diagnostics are issued.

This permits sibling expressions to solve one another.

### `Option`

```text
Some 1
  T = Int from the payload
  result = Option Int refined to Some
```

```text
None
  no payload evidence
  expected Option Int supplies T = Int
```

A context-free `None` still fails when its checking unit ends with `T` unresolved.

### `Result`

`Result` demonstrates why constructor-local inference cannot always finish immediately:

```text
Ok 1
  T = Int
  E remains unknown
```

Inside a branch expression such as:

```text
if condition
  then Ok 1
  else Error "failed"
```

the two results constrain one family instantiation:

```text
Ok branch:    Result Int ?E
Error branch: Result ?T String
joined result: Result Int String
```

Neither branch needs an explicit type argument. A lone context-free `Ok 1` remains ambiguous because its error type never becomes known.

This is constraint solving within one expression, not polymorphic generalization.

### Collections may provide the same context

Conceptually:

```text
List of
  None
  Some 1
```

can infer a homogeneous `(List (Option Int))`. The `None` constructor’s temporarily unknown parameter is solved by the other element before the enclosing list expression finishes checking.

The checked program then supplies the resolved `Int` instantiation to both runtime values.

## 4. No constructor-specific let-polymorphism

Aloe should not generalize:

```text
none : for every T, Option T
```

or:

```text
ok-one : for every E, Result Int E
```

A bound value has one monomorphic instantiation.

Allowing immutable constructor values to generalize while ordinary function and object values remain monomorphic would add:

- Type schemes in value environments.
- Instantiation at every variable use.
- A value restriction or constructor-specific exception.
- Complications for runtime generic identity.
- Ambiguous reflection of one value at multiple types.

Expected typing and explicit construction-site instantiation solve the practical problem more locally.

A programmer who needs `None` at two types constructs it twice, just as a polymorphic constructor message is freshly instantiated on each send.

## 5. Refinements form constructor-set knowledge

For a concrete family `F A`, the checker may additionally know a possible-constructor set `S`.

```text
F A @ S
```

is explanatory notation only.

For `Option Int`:

```text
Option Int @ {Some}        more precise
Option Int @ {None}
Option Int @ {None, Some}  unrefined
```

The refinement is not part of nominal identity. All three remain values of the same invariant type `Option Int`.

### Refinement operations

| Situation | Constructor-set operation |
|---|---|
| Direct constructor | Singleton set |
| Explicit case branch | Intersection with that constructor |
| Default branch | Remove explicitly handled constructors |
| Alternative branch results | Union |
| Widening to family | Replace with the full constructor set |
| Conversion to protocol | Forget constructor knowledge |
| Impossible branch | Empty intersection, therefore unreachable |

A smaller set means more knowledge. Forgetting knowledge is always safe.

This is not a subtype hierarchy:

- Cases cannot be named as parameter types.
- Overloads cannot select `Some T` as a nominal subtype.
- Constructor-set inclusion does not affect runtime family identity.
- The runtime value already carries the actual constructor tag; no refinement object is stored.

## 6. Refinements are initially shallow

The initial checker should track constructor knowledge only for the outer value being described.

For example:

```text
Some (Leaf 1)
```

may establish:

```text
outer value: Option (Tree Int), refined to Some
payload type: Tree Int
```

It does not establish a persistent generic type resembling:

```text
Option (Tree Int refined to Leaf)
```

Similarly, a list containing only `Some` values remains nominally:

```text
List (Option T)
```

rather than acquiring a non-source-writable element type for “lists of only `Some`.”

This shallow rule prevents refinement facts from becoming hidden generic arguments that alter:

- `cons` compatibility.
- Invariance.
- Function signatures.
- Collection type identity.
- Reflection.
- Diagnostic rendering.

More precise collection-wide knowledge would require relational or dependent typing and is not justified by the current applications.

## 7. Where shallow refinement is preserved

Outer refinement knowledge should survive direct immutable aliases:

```text
construct Some
bind it to x
use x’s Some-local surface
```

This includes direct `let` bindings despite `let` remaining exactly `fn` plus `call`. The checker must carry the argument’s occurrence fact into that immediately checked lexical binding; this does not give `let` a second evaluation meaning.

Refinement is preserved through:

- A direct constructor expression.
- An inferred alias of that expression.
- The whole-value binder of a case branch.
- `self` in constructor-specific method bodies.
- A branch result when every possible result preserves compatible knowledge.

Refinement is normally forgotten through:

- A source annotation naming only the family.
- A declared method or factory result type.
- A protocol conversion.
- Storage behind an ordinary generic parameter.
- A payload whose declaration names only the family.
- Reflection without a checked concrete subject type.

An ordinary method’s implementation does not leak refinement through its declared result. If a factory declares `Option T`, callers receive `Option T`, even if its body currently always constructs `Some`.

Locally inferred expression checking may retain enough occurrence knowledge to validate an immediate use. Refinements do not become reusable, source-visible function contracts in the initial model.

## 8. Branch-result unification

Case and conditional branches combine two independent things:

1. Their ordinary Aloe types.
2. Their outer constructor refinements, when those types are the same family.

### Ordinary type constraints

The underlying types must unify normally:

- Same nominal declaration.
- Same number of generic arguments.
- Invariant arguments.
- Normal type-variable solving.
- Expected protocol conversion when supplied by context.
- No automatic search for a common protocol.

### Refinement join

After the underlying family types unify, branch refinements join by union.

```text
Some branch → Option Int @ {Some}
None branch → Option Int @ {None}

result → Option Int @ {Some, None}
```

If every reachable branch returns `Some`, the result may retain `{Some}`.

If one branch returns an unrefined `Option Int`, the joined result is unrefined because that branch may produce any constructor.

### Expected types still guide construction

A generic method such as `Option.map` might promise `Option U`. That expected result allows its `None` body to instantiate the payload-free constructor at `U`, while the `Some` body constrains the same `U` from the mapped payload.

Likewise, a generic fold promising `R` checks every case body against one rigid method instantiation of `R`.

Branch order must not affect inference or diagnostics.

## 9. Protocol-valued branch results

Aloe should retain its existing bidirectional discipline.

If branches produce unrelated nominal families that conform to the same protocol, the checker does not invent that protocol as their least upper bound.

For example:

```text
branch one: Sym
branch two: Prod
```

does not infer `Math` merely because both currently conform to it.

The expression succeeds when context expects `Math`:

```text
expected result: Math
```

Each branch is then independently checked for conformance.

This avoids open-world searches whose result could change when declarations or protocols are added.

## 10. Recursive nominal families

Aloe should support recursive payload types through nominal self-reference.

`Tree T` is well formed because its `Branch` payload refers to the same nominal family:

```text
Branch (Tree T) (Tree T)
```

The checker does not unfold `Tree T` into its constructors during ordinary type comparison. Two tree types match by:

1. Exact declaration identity.
2. Equal generic arity.
3. Invariantly unified arguments.

Constructors introduce recursive values, and case elimination observes one constructor layer. There is no general fold/unfold type operator.

This keeps unification finite:

```text
Tree Int = Tree Int
Tree Int ≠ Tree Float
```

The checker never attempts to equate `Tree Int` with a structural sum describing `Leaf` and `Branch`.

## 11. Recursive well-formedness

A declaration’s family header and constructor identities become available while its payload types and methods are checked. This permits direct self-reference without a separate forward declaration.

Initial recursive families follow these rules:

1. The recursive reference must name the same declaration identity.
2. It must supply the declaration’s full generic arity.
3. Its arguments must be the same in-scope family parameters in the same order.
4. It may appear beneath nested inside another already-known type.
5. It may appear inside a function type.
6. Constructor payloads and methods must otherwise contain well-formed Aloe types.

Valid examples include:

```text
Tree T
  Branch (Tree T) (Tree T)
```

and:

```text
Rose T
  Node T (List (Rose T))
```

Initially invalid recursive shapes include:

```text
Tree T
  Strange (Tree (List T))
```

and recursive parameter permutations such as:

```text
PairTree A B
  Swap (PairTree B A)
```

Those are forms of non-regular or polymorphic recursion. They are expressive, but they complicate inference and recursive method checking without serving the current applications.

## 12. Direct recursion first; mutual recursion later

The initial model should permit:

- References to previously declared types.
- Direct regular self-reference.

It should not initially introduce mutually recursive declaration groups or forward type references.

Mutual recursion would require decisions about:

- Declaration grouping.
- Simultaneous identity registration.
- Cross-family constructor visibility.
- Error recovery for partially valid groups.
- Surface syntax.

`Tree`, recursive options, and recursive list-like structures do not require it. Mutual families can be added later if a real vocabulary needs them.

## 13. No strict-positivity requirement initially

Aloe is not a total language or proof assistant. Methods may already recurse indefinitely, and the type system does not derive induction principles or prove termination.

Therefore a recursive reference need not initially be restricted to mathematically positive positions. A payload containing a function that mentions the family remains an ordinary immutable payload.

Adding positivity analysis would be justified if Aloe later gains:

- Derived structural recursion.
- Termination checking.
- Automatic variance.
- Logical propositions or proofs.
- Generic recursion schemes whose soundness depends on positivity.

Until then, regular nominal identity is sufficient for type safety.

For that reason, the design should call these **recursive nominal algebraic families**, not claim that Aloe has a full theory of inductive types.

## 14. Recursive methods

Family message signatures are registered before their bodies are checked, allowing recursive sends.

For `Tree T`, operations such as `map`, `fold`, and `size` may use Decision 3’s case-complete bodies:

- A `Leaf` body consumes its `T`.
- A `Branch` body recursively sends the family message to its `Tree T` children.

Method-local generic parameters remain rigid within one body check and freshly instantiated at each external send.

For example, a conceptual `map` has one `U` shared throughout a given invocation:

```text
map : (T → U) → Tree U
```

Recursive calls on both children must produce the same `Tree U`.

Aloe does not check that recursion is structural or terminating.

## 15. Recursive elimination

Decision 4’s flat case form is sufficient for recursive types.

A tree consumer:

1. Eliminates one `Tree T`.
2. Receives `T` in `Leaf`.
3. Receives two unrefined `Tree T` values in `Branch`.
4. Recurses or performs nested elimination explicitly.

Exhaustiveness remains finite because it concerns the declaration’s finite constructor set, not the potentially unbounded depth of runtime values.

Adding a new tree constructor produces the same missing-case and missing-method diagnostics as any nonrecursive family.

## 16. Does recursion belong in the first implementation slice?

No.

Recursive types are part of the approved semantics, but they should not be required in the first algebraic-data implementation slice.

The first slice should establish the nonrecursive foundation:

- One-constructor product parity.
- Multiple constructors under one nominal family.
- Generic constructor inference.
- Payload-free expected construction.
- Singleton refinement.
- Exhaustive elimination.
- Branch-result unification.

`Option T` exercises nearly all of those rules with minimal representation complexity. `Result T E` then tests partially inferred family parameters.

`Tree T` should follow in a separate slice after the nonrecursive model is green. It adds self-registration, recursive payload checking, recursive method bodies, nested elimination, and recursive presentation pressure. Keeping it separate makes implementation evidence easier to interpret.

The exact checkpoint sequence still waits for the remaining semantic and syntax decisions.

## Alternatives considered

### Covariant immutable families

Covariance would make some producer-only families convenient, but message parameters and overloads quickly invalidate that assumption. Explicit or inferred variance can be revisited after real APIs demonstrate a recurring reconstruction burden.

Recommendation: invariant initially.

### A bottom type for payload-free constructors

`None` could be assigned something resembling `Option Never` and widened covariantly. This requires both a bottom type and covariance, neither of which otherwise has application pressure.

Recommendation: expected typing and explicit instantiation.

### Generalized constructor values

`None` and `Ok 1` could be let-polymorphic. This adds type schemes and complicates runtime identity.

Recommendation: monomorphic values; polymorphic constructor messages.

### Deep refinement types

Collections and nested generic arguments could remember exact constructors. This is expressive but changes ordinary generic method behavior and approaches dependent typing.

Recommendation: shallow outer-value refinements.

### Equirecursive types

The checker could equate a recursive type with its unfolded representation. That adds recursive type equivalence and potentially nonterminating unification.

Recommendation: exact nominal identity; constructors and case provide the only representation boundary.

### Unrestricted polymorphic or mutual recursion

These are plausible later extensions but require more inference and declaration machinery than `Tree T` needs.

Recommendation: direct regular self-recursion first.

## Decision 5 recommendation

Approve the following:

- Nominal generic families are invariant.
- Constructor sends infer one exact instantiation from explicit, expected, payload, and enclosing-expression constraints.
- Temporarily unresolved parameters may be solved across sibling expressions.
- Unresolved parameters may not escape a checking unit.
- Constructor results are not let-generalized.
- Refinements are constructor-set knowledge, not nominal subtypes.
- Refinement joins use set union; branch restriction uses intersection.
- Refinements are initially shallow and do not become generic type arguments.
- Direct immutable aliases preserve outer refinement; declared abstraction boundaries may forget it.
- Branch result typing retains ordinary bidirectional unification and performs no automatic common-protocol search.
- Recursive families use regular nominal self-reference with the same parameters.
- Recursive nominal types are not unfolded during unification.
- Direct self-recursion is supported; mutual and polymorphic recursion are deferred.
- No positivity or termination claim is made.
- Recursive types are semantically supported but deferred beyond the first implementation slice.
